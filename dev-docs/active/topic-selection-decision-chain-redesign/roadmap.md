# Topic Selection Decision Chain Redesign - Roadmap

## Goal
- 基于 `automated_topic_notes.md`，将现有“自动化选题”设计重构为 **LLM 主导、人在关键节点回路中确认的选题决策链路**。
- 产出一份可持续迭代的设计说明，后续再拆分实现任务。

## Framing
- 本任务不追求“全自动选题”。
- 大模型承担检索扩展、证据抽取、聚类、反证、对比、包装与风险暴露。
- 人负责研究兴趣、资源边界、真实需求、研究切口、价值判断与晋升决策。
- 设计目标是提高选题决策质量，而不是提高题目生成数量。

## Non-goals
- 不在本任务包内直接修改代码、数据库 schema、OpenAPI 或桌面 UI。
- 不把 LLM 设计成具有最终学术判断权的 agent。
- 不把 `retrieval-topic`、`title-card`、`paper-project` 的现有实现语义立即推翻重做。
- 不把设计文档写成一次性 PRD；它应作为后续讨论和任务拆分的 SSOT。

## Open Questions
- 当前设计轮次无未决 open question。
- 已关闭问题记录：
  - Q1 resolved: `SearchPlan` v1 不需要独立全屏 UI；先在 title-card/reviewer workbench 中以 plan panel、coverage matrix、blocker/recheck 卡片和 trace drilldown 呈现。独立 UI 只有在后续审查负载证明必要时再拆。
  - Q3 resolved: value gate hard blockers 不采用宽泛 owner override；统一走 `BlockerPolicy`。`non_overridable` 只能修复/重跑，`overrideable_with_risk` 必须形成 `HumanOverride + accepted risk`，`escalation_only` 必须升级人审或 focused review。
  - Q4 resolved: promotion 到 `PaperProject` 前不额外强制一个 research-argument readiness gate。选题侧的必经 gate 是 `PromotionDecision`；`TopicPackage`、`PromotionCommitmentProfile` 和 `PaperProjectBridge` 交接 trace、conditions 和 early checks，下游 research-argument/writing 模块通过 feedback/recheck event 回传问题。
  - Q5 resolved: `LiteratureResourcePool` 是显式概念读模型和可快照输入；v1 可由现有 literature repository、auto-pull suggestions、imported records 和人工导入聚合生成，不必先作为新的 canonical 写模型。`SearchPlan` / `SeedDiscoveryRun` 必须消费其 snapshot 和 provenance。

## Recording Policy
- 只记录有持续指导意义的设计决策、边界、未决问题和验收标准。
- 不记录低价值过程信息，例如逐轮对话摘要、临时措辞、已被后续决策取代的中间说法。
- 被取代的设计只在会影响后续判断时保留，并明确标记为 superseded。

## Decision Record
- D1: 本任务不追求全自动选题；目标是 LLM 主导、人关键节点在回路的选题决策链路。
- D2: 旧版 `idea -> evidence -> need -> slice -> question -> value -> package -> promotion` 作为语义主线保留，但新版必须是带回路的研究决策系统，不是线性 pipeline。
- D3: `SearchPlan` 是选题决策链路的第一步正式对象；`TopicSeed/title-card intent` 是入口意图，文献供给链路是上游输入。
- D4: auto-pull 只消费文献导入设置并形成 `LiteratureResourcePool`；`SearchPlan` 消费资源池及其 provenance，不直接驱动 auto-pull。
- D5: `SearchPlan` 不是参数容器；它的核心价值是覆盖假设、风险登记、审查标准和 provenance contract。
- D6: `SearchPlan` 挂在 `title-card` 下，必须版本化；被用于 EvidenceMap 后不得原地覆盖。
- D7: `SearchPlan` 可以触发 one-off SearchRun，但不改写 auto-pull/import settings；下游对象在核心 coverage boundary 变化时进入 `recheck_required`。
- D8: `SearchPlan` 的持久化采用本地 DB 为主、artifact store/本地文件为辅；LLM 大体量原始材料只作为 artifact，DB 保存状态、引用和校验信息。
- D9: `SearchPlan` 相关 LLM 动作限定为生成、扩展、诊断、批判、修订、解释和 recheck impact 标记；LLM 不批准 promotion，不改写 auto-pull/import settings。
- D10: `SearchRun` 是某个 `SearchPlan.version` 的执行 provenance，不是 SearchPlan 产生的 LLM 推理结果；LLM 推理材料归入 artifact/ref，除非它服务于 run 内的 relevance/rerank 等执行步骤。
- D11: `SearchRun` 的主要数据来源是 `SearchPlan.version`、`LiteratureResourcePoolSnapshot`、本地/外部检索源和执行时 artifacts；主要消费方是 EvidenceMap builder、plan review、NeedCandidate、falsification、value assessment、audit/re-run 和 UI。
- D12: `SearchRun` 必须支持复现、结果 accounting、排除理由、去重 provenance、source health、must-check accounting、coverage delta、LLM execution artifact、quality sampling 和 re-run comparison。
- D13: EvidenceMap 的最小单元是 claim-level `EvidenceUnit`，不是 paper 或文本 chunk；推荐粒度是 `one source + one claim/signal + one role + one locator`。
- D14: EvidenceUnit 服务于 topic value judgment；paper 是 evidence source container，不是选题价值判断单元。
- D15: Claim v1 作为 `EvidenceUnit.claim` payload，不单独建顶层对象；结构必须分离 source statement、normalized statement、interpretation、scope、qualifier、comparison、topic relevance、provenance 和 review。
- D16: Claim 采用“结构化 + 描述”的双表示；structured fields 是权威事实/计算层，narrative fields 是受约束的 LLM-facing 语料，不能引入结构化字段外的新事实。
- D17: Claim narrative 的来源是论文中的高价值内容，但必须 locator-backed，并只保留对 topic value judgment 有用的 evidence content，不做整篇论文摘要。
- D18: EvidenceUnit 数据来源由 SearchRun selected/candidate refs、LiteratureResourcePool provenance、locator-backed high-value source content、LLM extraction artifacts 和 human review notes 组成；unit 字段按 identity/provenance/claim/topic_linkage/quality/review/lifecycle 分组。
- D19: EvidenceMap v1 采用结构化列表 + typed links + clusters，而不是复杂图数据库；MapSummary 只作为 LLM/UI 消费视图，不替代 EvidenceUnit。
- D20: EvidenceMap 防污染依赖 source separation、no abstract-only evidence、claim-level dedup、challenge preservation、scope/baseline/source-quality guard、sampling review、conflict sets 和 staleness/recheck 状态。
- D21: EvidenceMap 可以产出 evidence quality / coverage quality / map quality / readiness signals，但不能直接产出 topic value、publishability、contribution strength 或 promotion decision。
- D22: EvidenceMap 的直接消费方是 NeedCandidate、ValidatedNeed falsification、ResearchSlice、TopicQuestion、TopicValueAssessment、TopicPackage 和 UI；PromotionDecision/PaperProject 只能通过摘要或 TopicPackage 间接消费。
- D23: EvidenceMap refresh/recheck 由上游覆盖变化、证据质量变化、下游挑战和人工操作触发；`stale` 表示可能过期，`recheck_required` 表示可能影响 Need/Question/Value，`frozen` 表示审计快照不可覆盖。
- D24: SearchRun 需要独立持久化为本地 DB 对象，不能只复用普通日志；它承载 `SearchPlan.version -> EvidenceMap` 的执行 provenance、状态机、结果 accounting、source health、dedup、must-check 和 re-run comparison。
- D25: EvidenceMap/EvidenceUnit/TypedLink/Cluster/Pattern/ConflictSet 应进入本地 DB；claim、summary、quality、coverage_delta 等可先作为 JSON payload，但关键查询字段必须列化或可索引。
- D26: EvidenceUnit/claim v1 跟随 EvidenceMap 存在，但 source/provenance/claim payload 应稳定；频繁操作发生在关系层和状态层，修正 claim 本体必须 version/supersede，不应原地覆盖。
- D27: EvidenceUnit 不因丢弃或晋升而物理移动/删除；丢弃用 rejected/out_of_scope/superseded 状态，晋升保存 selected refs + map version + necessary snapshot。
- D28: NeedCandidate 是从 EvidenceMap 提炼出的潜在未满足需求方向，用于承载待验证假设；它不是已成立需求，不能直接进入 ResearchSlice/TopicQuestion。
- D29: NeedCandidate 需要作为本地 DB 持久化对象存在；它是 LLM 深度参与的方向假设工作区，必须保存 support/challenge refs、LLM rationale、合并/拒绝/搁置历史和 review 状态。
- D30: NeedCandidate 的核心作用是 direction extraction、hypothesis workspace、LLM reasoning surface、debias buffer 和 negative memory。
- D31: Candidate -> ValidatedNeed 是迭代过程；NeedCandidate 可多轮 challenge、merge、scope revise、evidence gap、SearchPlan recheck 和 new iteration，只有 `ready_for_validation` 才能进入 ValidatedNeed adjudication。
- D32: NeedCandidate 可以反向影响 SearchPlan，但通过 `SearchPlanRecheckRequest` 表达 coverage gap / missing baseline / missing community / terminology gap，不直接改写 SearchPlan。
- D33: `ProposeSearchPlanRevision` 是 NeedCandidate/validation challenge 触发的受控工具，输出 proposed SearchPlan diff、must-check/query/rule 更新和 recommended SearchRun；它不自动改写 SearchPlan，必须经 reviewer accept 后生成 vNext。
- D34: NeedCandidate 鲁棒性主要取决于 LLM 工作流稳定性和 SearchPlan revision 回路有效性；前者要求 generator/skeptic/comparator/reviewer 等角色、结构化输出和多 agent 分歧保留，后者要求 coverage gap 能转化为可执行 SearchPlan diff 并实际丰富 EvidenceMap。
- D35: NeedCandidate 状态机暂不增加人工创建路径；rank 不作为稳定事实，仅作为排序快照/assessment artifact；ValidatedNeed 作为新对象创建并引用 source NeedCandidate。
- D36: `ready_for_validation` 是进入裁决的 gate，不代表需求成立；它要求 support/challenge/coverage/scope/pseudo-gap 风险显式化，且无 open high-priority SearchPlanRecheckRequest。
- D37: Candidate 废弃和 seed/title-card 关闭必须记录原因与引用；关闭不是删除，后续可因新证据、新约束或新 SearchPlan reopen。
- D38: `ready_for_validation` 不由简单投票决定；采用专门的 `AssessCandidateReadiness` gate workflow，以 checklist、hard blocker、cited rationale 和 artifact refs 作为状态转移依据。该状态默认 agent_actionable with escalation；只有高风险、高不确定性、强分歧、open coverage risk 或需要 accepted risk 时升级人审。
- D39: `ready_for_validation` 必须经过 `ValidateNeedAdjudication` workflow；该 workflow 总是产出 `ValidateNeedAdjudicationResult`，只有 `final_decision=validate` 且人确认后才创建 `ValidatedNeed`。
- D40: `ValidatedNeed` 是 evidence-version-bound 的强研究判断，不是永久事实或 topic value；它应引用 source NeedCandidate、`ValidateNeedAdjudicationResult`、EvidenceMap/SearchPlan/SearchRun 版本和 decision support packet，并可随关键证据变化进入 `recheck_required/challenged/superseded/retracted`。
- D41: `ValidateNeedAdjudication` 必须产出 `ValidationDecisionSupportPacket` 辅助人类确认，并产出 `ValidateNeedAdjudicationResult` 记录最终处置；证据包是引用型审查视图，不是新事实来源，必须先呈现 strongest support、strongest challenge、coverage/open risks，再给 recommendation。
- D42: NeedCandidate 生成应定义为 evidence-constrained hypothesis generation，而不是开放式 brainstorm；每个 candidate 必须绑定 evidence signals、scope、prior-art/negative-memory check、pseudo-gap critique 和 required rechecks。
- D43: Candidate 被否定、部分解决、证伪、合并、搁置或验证后应形成 `CandidateDecisionMemory`；它作为下一轮生成/质疑的上下文和反证压力，不作为新的 evidence，使用时必须追溯到原 EvidenceUnit/SearchRun/reviewer artifact。
- D44: `ResearchSlice` 是从 `ValidatedNeed` 到 `TopicQuestion` 的收束层，解决真实需求过宽、多个需求聚合/拆分、贡献形态选择、资源边界和排除边界问题；它消费 ValidatedNeed、decision support packet、EvidenceMap、SearchPlan/SearchRun provenance、decision memory 和人的资源/社区约束，产出 selected slice、included/excluded boundaries、contribution candidates、resource/baseline assumptions、rationale 和 open risks。
- D45: `ValidatedNeed` 是产出 `ResearchSlice` 的必要输入但不是充分输入；不能默认可靠地直接生成唯一 slice，应通过 `PlanResearchSlice` workflow 先生成和比较 `ResearchSliceOptionSet`，再由 `SelectResearchSlice` 选择、请求更多 options、park 或 reject。该选择可由 agent 执行并持久化 rationale/open risks，只有在高不确定性、强分歧、资源/社区冲突或 baseline 风险高时升级为 human review。
- D46: `PlanResearchSlice` 的目标是生成可比较的 `ResearchSliceOptionSet`，不是直接产出最终 slice；其输入必须包含 ValidatedNeedBundle、decision support packet、EvidenceMap context、SearchPlan/SearchRun provenance、CandidateDecisionMemory 和 ResearchConstraintProfile，动作包括 need bundle 归一化、切分轴提取、option 生成、边界/证据/baseline/可行性/claim shape 检查和 option critique。
- D47: `ResearchSliceOptionSet` 中每个 option 必须绑定 source ValidatedNeed、included/excluded boundaries、evidence alignment、baseline/resource assumptions、evaluation path、expected/fallback claim、risk profile、why_choose/why_not_choose、confidence 和 human review trigger；无 excluded boundaries 或无 evidence/need 绑定的 option 不合格。
- D48: `PlanResearchSliceRun`、`ResearchSliceOptionSet`、`SliceSelectionDecision` 和 `ResearchSlice` 都应进入本地 DB；LLM prompt/response、长篇比较和诊断进入 artifact，但 DB 必须保存输入快照、workflow/model/prompt 版本、option identities、选择/拒绝理由、open risks、human review trigger 和下游 recheck 状态。
- D49: `ResearchConstraintProfile` 应作为 versioned/snapshot-able DB 对象参与 `PlanResearchSliceRun`；约束变化不改写历史 option set，而是触发新的 planning run。EvidenceMap/ValidatedNeed/SearchPlan/SearchRun 关键版本变化会将相关 option set、selection decision、ResearchSlice 和下游 TopicQuestion/ValueAssessment 标记 `recheck_required`。
- D50: `PlanResearchSlice` 应支持 LLM deep participation 和 multi-agent multi-round debate；推荐角色包括 SlicePlanner、BoundaryCritic、EvidenceGroundingCritic、BaselineCritic、FeasibilityCritic、ClaimShapeCritic、SynthesisAgent。辩论不是投票，必须绑定 evidence/constraint/baseline refs，并保留 unresolved disagreements 和 human review triggers。
- D51: `SlicePlanningDebateSession` 应作为 `PlanResearchSliceRun` 的子对象进入本地 DB；DB 保存角色、轮次摘要、关键 objections、accepted/unresolved disagreements、human review triggers 和 transcript artifact refs，完整 prompt/response/transcript 作为 artifact。
- D52: `SliceSelectionDecision` 是从 option set 到 ResearchSlice 的可审计选择决策，不只是 selected option 字段；它必须先排 hard blockers，再评估 constraint/evidence/feasibility/claim/risk fit，输出 select/request_more_options/park/reject、rejected option reasons、loopback target、required actions、confidence 和 human review trigger。
- D53: `SliceSelectionDecision` 采用三层判定模型：hard gate 决定 option 是否可选，comparative fit 在可选 options 之间比较 need/evidence/constraint/feasibility/claim/strategy/risk fit，synthesis decision 决定 select、request_more_options、park 或 reject；不能把 selection 简化为单一评分、投票或摘要。
- D54: `SelectResearchSlice` 也应支持 multi-agent review，但目标是审查现有 option set 而不是继续发散；推荐角色包括 GateReviewer、ConstraintFitReviewer、EvidenceFitReviewer、FeasibilityReviewer、ClaimRiskReviewer、StrategyReviewer、DecisionSynthesizer。该过程不是投票，hard blocker 和高严重度分歧优先于多数偏好。
- D55: `SliceSelectionReviewSession` 应进入本地 DB，作为 `SliceSelectionDecision` 的审查依据；DB 保存 reviewer roles、per-option assessments、hard blocker disagreements、unresolved disagreements、human review triggers 和 transcript artifact refs。
- D56: `SliceSelectionDecision` 必须支持回流；`request_more_options/park/reject` 必须带 loopback_target 和 required_actions，`select` 后也可被 TopicQuestion/TopicValueAssessment 或新证据回流到 selection、PlanResearchSliceRun、ResearchConstraintProfile、ValidatedNeed、EvidenceMap 或 SearchPlan。回流不覆盖旧决策，应创建新 decision/run/version 并保留历史依据。
- D57: 回流链路应作为规划信号被利用：改进 slice axes/options、澄清 ResearchConstraintProfile、触发 EvidenceMap/SearchPlan recheck、沉淀 CandidateDecisionMemory/planning memory，并评估 agent/prompt 质量；同时必须设置 retry budget、stop condition 和“无新增信息不得重复运行”的防死循环规则。
- D58: `ResearchSlice` 是由 `SliceSelectionDecision(select)` 产生的 versioned downstream contract，定义本轮研究准备切入的可执行 problem space；它必须保存 source option/selection provenance、included/excluded boundaries、claim shape、resource/data/evaluation/baseline assumptions、usage contract 和 recheck/supersession 状态。
- D59: `ResearchSlice` 的主要用法是约束 `TopicQuestion`、供 `TopicValueAssessment` 评估、作为 `TopicPackage` 的边界快照和 UI/recheck 锚点；它不是论文标题、topic value、publishability 判断，也不能直接晋升 PaperProject。
- D60: 每个 `ResearchSlice` 必须具备 resource trace，能回溯到 support/challenge/claim EvidenceUnits、原论文或其他 source、baseline evidence、dataset/resource/tool/code refs 和 LLM/review artifacts；paper/source 是来源容器，不能替代 claim-level EvidenceUnit。相关 EvidenceUnit 或 source health 变化时，ResearchSlice 应进入 `recheck_required`。
- D61: ResearchSlice 相关表结构应拆成核心决策表、planning/selection provenance 表和资源追溯表；核心建议包括 `TopicResearchSlice`、`TopicResearchSliceOptionSet`、`TopicResearchSliceOption`、`TopicSliceSelectionDecision`、`TopicResearchSliceEvidenceRef`、`TopicResearchSliceSourceRef`、`TopicResearchSliceBoundary`、`TopicResearchSliceAssumption` 和 `TopicResearchSliceArtifactRef`。关键引用/状态/风险/回流字段必须列化，长篇细节可放 JSON/artifact。
- D62: `FormTopicQuestion` 负责将 `ResearchSlice` 转为可回答的研究问题合同；它消费 problem_space、slice_statement、included/excluded boundaries、target setting/community、preferred contribution type、expected/fallback claim、observable success criteria、data/evaluation/baseline assumptions、resource_trace 和 usage_contract，产出 main question、sub-questions、contribution hypothesis、answerability plan stub 和 boundary/traceability check。
- D63: `TopicQuestion` 不能只是 ResearchSlice 的问句改写，也不能引入新的 unmet need；它必须绑定 source ResearchSlice.version，并提供最小 answerability plan。若问题超出 slice 边界或无法回答，应回流 ResearchSlice；若失败源于证据、baseline 或约束不足，再回流 EvidenceMap/SearchPlan/ResearchConstraintProfile。
- D64: 一个 `ResearchSlice` 可以产生多个 `TopicQuestion` 候选；`FormTopicQuestion` 应先产出 `TopicQuestionCandidateSet`，再通过 `SelectTopicQuestion` 准入一个或多个候选进入 TopicValueAssessment。每个 TopicQuestion 必须独立保存 boundary check、answerability plan stub、claim alignment 和 review 状态，不能共享模糊判断。
- D65: `FormTopicQuestion` 应实现为独立、可审计的 workflow run，而不是单次 prompt；它冻结 ResearchSlice/version、resource trace、EvidenceMap/SearchPlan/SearchRun 版本、ResearchConstraintProfile 和上游审查 artifacts 作为 input snapshot，产出候选问题集，不直接改写 ResearchSlice 或 EvidenceMap。
- D66: `FormTopicQuestion` 的 agent workflow 推荐包含 QuestionFramer、CandidateGenerator、AnswerabilityPlanner、BoundaryGuardian、EvidenceTraceReviewer、ClaimShapeReviewer、CommunityFitReviewer 和 QuestionSynthesisAgent；该过程综合 objections，不做简单投票。
- D67: `SelectTopicQuestion` 采用 hard blockers -> admission/readiness review -> disposition decision；阻断项包括新 unmet need、边界违规、缺失最小 answerability path、核心内容无法追溯且未标为 assumption、expected claim 过强。输出可为 admit/admit_multiple/merge_then_admit/park/reject_all/no_admissible_candidate。
- D68: TopicQuestion 形成阶段应持久化 `FormTopicQuestionRun`、`QuestionFormationReviewSession`、`TopicQuestionCandidateSet` 和 `TopicQuestionSelectionDecision`；DB 保存身份、版本、状态、引用、阻断项、选择理由和 artifact refs，完整 prompt/response/transcript 进入 artifact store。
- D69: `FormTopicQuestion` 的鲁棒性应从 input readiness gate 开始；ResearchSlice 若缺失 stable boundaries、resource trace、claim shape、evaluation path 或 constraint snapshot，应输出 needs_slice_revision/needs_constraint_clarification，而不是继续生成问题。
- D70: TopicQuestion 候选必须从冻结的 `QuestionFrame` 派生，并区分 evidence-backed fields 与 assumptions；assumption 只能作为风险保留，不能被当作 evidence support。
- D71: `FormTopicQuestion` 应使用 bounded candidate diversity、role-separated review、deterministic validators、negative question memory、re-run comparison、loopback classification 和 human review triggers 防止越界、不可回答、重复失败和不稳定推荐。
- D72: `SelectTopicQuestion` 是从 `TopicQuestionCandidateSet` 到一个或多个 `TopicQuestion` 的可审计准入与处置决策，不是 candidate set 的推荐字段；它不判断最终 topic value、publishability 或 PaperProject promotion，也不默认多选一。
- D73: `SelectTopicQuestion` 消费 candidate set、FormTopicQuestion input snapshot、source ResearchSlice、Evidence refs、ResearchConstraintProfile、negative question memory 和 downstream readiness hints；其目标是判断哪些候选问题满足进入 TopicValueAssessment 的最低合同，哪些需要合并、搁置或拒绝。它不拥有回流机制；上游问题只记录为 blocking context。
- D74: `SelectTopicQuestion` 采用 hard gate -> per-candidate admission/readiness review -> candidate relationship review -> admission disposition decision；hard gate 覆盖 refs/version、边界、新 need、answerability、traceability、claim strength、negative memory 和 stale/recheck_required 输入。
- D75: 通过 hard gate 的候选不需要互相淘汰；集合关系审查关注 duplication/overlap、conflict、complementarity、dependency、portfolio risk 和 optional priority。priority 只在资源受限、候选重叠或下游评估容量有限时作为调度信号。
- D76: `TopicQuestionSelectionDecision` 输出 admit/admit_multiple/merge_then_admit/park/reject_all/no_admissible_candidate、admitted ids、hard gate results、admission review、candidate relationships、rejected reasons、blocking contexts、human review triggers、confidence 和 created TopicQuestion refs；不写 loopback target 或 required actions。
- D77: 从 ResearchSlice 到 TopicQuestion 的持久化应拆成 source boundary、formation run、question frame、candidate set/candidates、admission decision、materialized TopicQuestion、trace refs 和 artifacts；正式 TopicQuestion 不应承载完整 LLM 过程。
- D78: `TopicQuestionFrame`、`TopicQuestionCandidate`、`TopicQuestionSelectionDecision`、`TopicQuestionEvidenceRef`、`TopicQuestionBoundaryRef` 和 `TopicQuestionAssumptionRef` 应有稳定身份和可查询引用；长篇审查、prompt/response 和 transcript 进入 artifact store。
- D79: 现有 `TitleCardResearchQuestion` 可作为正式 `TopicQuestion` 演进，但当前 `researchSlice` 字符串和 JSON source refs 不足以支撑新链路；需要补充 source ResearchSlice/version、candidate、selection decision、answerability plan 和 trace ref 结构。
- D80: rejected/parked candidate 不删除；candidate disposition 和 selection decision 可派生 negative question memory，供后续 FormTopicQuestion 防止重复生成已知越界、不可回答或 claim 过强的问题。
- D81: `TopicQuestion` 和 `TopicQuestionCandidate` 仍必须能追溯到 `ValidatedNeed` / source `NeedCandidate`；该追溯通过从 `TopicResearchSliceNeedRef` 派生的 `TopicQuestionNeedRef` / `TopicQuestionCandidateNeedRef` 表达，是继承引用，不是重新验证需求。
- D82: 有了 admitted `TopicQuestion` 后，链路应明显收敛；下一步是对每个问题线性运行 `TopicValueAssessment`。线性表示控制流收敛，不表示价值判断简单。若准入多个问题，可分别评估，是否并行推进或择优进入 package 由后续阶段处理。
- D83: `TopicValueAssessment` 判断的是当前 question contract 是否值得现在投入；它不重写 TopicQuestion，不生成 title/package，也不直接创建 PaperProject。
- D84: `TopicValueAssessment` 消费 TopicQuestion、Need refs、ResearchSlice、EvidenceMap/EvidenceUnit refs、ResearchConstraintProfile 和 decision memory；输出 minimal gates、`ValueReasoningMemo`、ceiling/base/floor scenario sketch、top objections、`ValueDispositionDecision` 和可追溯原因。
- D85: `TopicValueAssessment` 的 minimal gates 只覆盖 value signal、non-solved sanity、answerability sanity、feasibility sanity 和 evidence sanity；核心难点在 evidence-backed value reasoning，包括 significance、originality、claim leverage、reviewer risk、effort-to-value fit、strategic fit 和 negative-memory check。
- D86: `TopicValueAssessment` 应先构造轻量 `TopicValueAssessmentInputSnapshot`；必需输入为 question contract、need trace、slice snapshot、evidence digest 和 constraint snapshot，可按需展开 EvidenceUnit locator、SearchRun/SearchPlan provenance、历史 assessment 和 reviewer artifacts。
- D87: `TopicValueAssessment` 不应默认消费全量论文全文、无关 EvidenceMap 节点、全部未准入候选或 TopicPackage/title candidates；这些会让线性裁决节点重新膨胀为探索节点。
- D88: `ValueReasoning` 的产物应是 `ValueReasoningMemo`，不是单纯分数表；memo 只能给 disposition recommendation，正式处置由 `ValueDispositionDecision` 承载，score 只能作为 UI/排序辅助，不能替代价值论证。
- D89: `ValueReasoningMemo` 必须覆盖 value thesis、significance、originality、claim leverage、reviewer risks、effort-to-value、strategic fit、negative memory check 和 disposition bridge，并要求关键判断绑定 refs 或显式 uncertainty。
- D90: `TopicValueAssessment` 默认由一个 ValueAssessor 生成 `ValueReasoningMemo`；仅当 `advance_to_package/drop` recommendation 高不确定、或存在 high severity reviewer objection 时，触发 focused critic review。critic 只审查价值论证薄弱点，不重新生成 TopicQuestion 或扩展上游检索。
- D91: `TopicPackage(draft)` 默认只从 `ValueDispositionDecision.decision = advance_to_package` 创建；`refine_question/refine_slice/park/drop` 不创建 package。如果多个 TopicQuestion 分别获得 `advance_to_package`，v1 每个 question 创建一个 draft package，后续由 PromotionDecision 组合、择优或晋升。
- D92: `TopicPackage` 是 handoff snapshot，不重新验证 need、不重新选择 ResearchSlice、不重写 TopicQuestion、不扩大边界，也不直接创建 PaperProject。
- D93: `TopicPackage` 消费 TopicQuestion、TopicValueAssessment/ValueReasoningMemo、Need refs、ResearchSlice、Evidence refs 和 ResearchConstraintProfile，产出 title candidates、research background、contribution summary、evaluation plan stub、evidence summary、risk register 和 handoff notes。
- D94: `TopicPackage` 的 trace/boundary check 必须确保 package 中的 title、claim、evaluation plan 和 risk 都可追溯到 question/value/slice/evidence refs；如果 package narrative 需要修改 question/claim/boundary/evaluation route，应作为 package draft issue 记录，不直接改上游对象。
- D95: 现有 `TitleCardPackage` 可作为正式 `TopicPackage` 演进；短期 JSON 可保留，但 source TopicQuestion、TopicValueAssessment、ResearchSlice.version、ValidatedNeed refs、selected Evidence refs、snapshot hash 和 artifact refs 应逐步结构化。
- D96: `TopicPackage` 是相对固定的收束/交接节点，不需要深入设计为新的探索流程；默认采用线性模板化 builder 和确定性 trace/boundary validation，LLM 只做 title、narrative 和 evaluation plan 表达整理，不新增 need/evidence/claim/boundary/verdict。
- D97: `PromotionDecision` 是从 `TopicPackage` 到 `PaperProject` 的显式人类授权 gate，不是新的价值评估节点；LLM 负责准备 dossier、发现 blocker、评估资源/策略并给 recommendation，但不能自动批准 promotion 或创建 PaperProject。
- D98: `PromotionDecision` 的判定采用 hard gate、conditional comparative review 和 commitment decision 三层；比较只在多个 package 竞争资源、重叠、可合并或需要排序时发生，不默认多选一。
- D99: `PromotionDecision` 输出 promote、promote_with_conditions、merge_packages、refine_package、reassess_value、revise_question、revise_slice、recheck_evidence_or_search、park 或 drop；所有非 promote 决策必须保存 typed loopback target、required actions、阻断原因和 source refs。
- D100: `PromotionDecision` 必须进入本地 DB；至少保存 package refs、decision type、decision maker、conditions、unresolved risks、loopback target、required actions、downstream project ref 和 artifact refs。`PromotionDossier` / `PromotionDecisionSupport` 可采用 DB summary + artifact 组合。
- D101: `PaperProjectBridge` 应作为本地 DB 对象持久化，用于从论文管理回溯选题管理；它只做已批准 package 到 PaperProject 的创建/关联与交接，不重新做选题判断。
- D102: `PaperProjectBridge` 采用 upstream refs + working-copy text + snapshot hashes 的策略：need/slice/question/value/evidence 保持引用，project brief/title/question/evaluation/risk 作为可编辑工作文本复制，package/promotion/project creation payload 保存快照 hash。
- D103: `TopicSeed` / `TitleCardIntentProfile` 是 `TitleCard` 下的 versioned intent contract，不直接等同于当前 `TitleCard`；`TitleCard` 继续作为 UI/聚合对象。
- D104: `TopicSeed` 只表达 raw/normalized intent、constraints、scope、source refs 和 search hints，不承载 ValidatedNeed、ResearchSlice、TopicQuestion、TopicValueAssessment 或 PromotionDecision。
- D105: `SearchPlan` 必须绑定具体 `TopicSeed.version`；seed 修改、拆分、关闭或重开不能静默影响旧 SearchPlan，应创建新 version 或 supersession 记录。
- D106: `NormalizeAndReviewSeed` 是进入 SearchPlan 前的轻量 gate，输出结构化 seed、clarification questions、SeedSplitProposal 和 ready_for_search_plan recommendation；LLM 可参与规范化和提示补全，但不得把假设写成人类约束。
- D107: `SeedDiscoveryRun` 是文献管理到选题入口之间的可选自动发现层，消费 LiteratureResourcePool、library index、metadata/fulltext/key-content、tags、clusters、citation/embedding signals、user research profile 和可选外部搜索，产出 `SeedCandidateSet`。
- D108: `SeedCandidate` 只是候选探索方向，不是正式 `TopicSeed`；它不能被 `SearchPlan` 直接消费，必须经 `NormalizeAndReviewSeed` 和人的确认/编辑后形成 `TopicSeed.version`。
- D109: `SeedDiscoveryRun` 必须持久化 input snapshot、source refs、cluster refs、query/search config、workflow/model/tool versions、quality notes 和 artifact refs，以便解释候选 seed 来自哪些文献和聚类信号。
- D110: LLM 可在 `SeedDiscoveryRun` 中执行搜索辅助、聚类解释、候选生成、去重和 critique，但推断出的用户偏好、资源约束、方法禁区只能作为 assumption，不能自动成为 human-confirmed seed constraint。
- D111: `SeedDiscoveryRun` 的鲁棒性依赖多路发现、反面信息、稳定性检查、证据密度检查、去重/合并和降噪策略；它不判断 topic value，只判断候选是否值得进入 seed review。
- D112: 每个 `SeedCandidate` 必须显式记录 why_not_explore、known_solved_risk、source_bias、cluster_instability、missing_constraints 和 pseudo-gap risk；候选漂移、单源支撑或热门词偏置应降低优先级或进入 parked/low_priority。
- D113: 全链路 recheck 采用事件驱动机制：LLM/workflow 输出结构化 `state_signals`，只有跨节点影响才创建 `RecheckEvent`，再由 `RecheckImpactAssessment` 转换为 affected object 的 no_impact/stale/recheck_required/invalidated。
- D114: `stale` 表示可能过期但不默认阻断，`recheck_required` 表示继续关键推进前必须处理，`invalidated` 表示核心依据失效并进入 retract/supersede/drop/new version 语义；closed/parked/dropped 是 lifecycle 状态，reopen 必须有新信息或 blocker resolution。
- D115: 关键 workflow input snapshot 必须包含 `input_state_context`，包括 source object versions、stale/recheck flags、open events、unresolved impacts、required actions 和 accepted risks；workflow output 必须包含 `state_signals`。
- D116: `RecheckEvent`、`RecheckImpact` 和 `RecheckResolution` 应进入本地 DB；LLM 不直接随意改全局状态，deterministic gate 和人工确认负责关键阻断、dismiss、override 或 resolution。
- D117: traceability 分为内容层 provenance、claim-level evidence、功能层 lineage 和下游 bridge/working copy；paper/source 是内容容器，TopicSeed/SearchPlan/ResearchSlice/TopicQuestion/TopicPackage 是功能容器，二者不能互相替代。
- D118: `EvidenceUnit` 是事实证据最小单元；正式下游对象必须同时保留 `FunctionalRef` / lineage 和 `EvidenceRef` / content provenance，事实性 LLM 输出必须绑定 evidence/content refs 或标记为 assumption。
- D119: 文献管理拥有内容资产和 source health，选题管理拥有 `TopicSeed -> PromotionDecision` 决策链路，论文管理通过 `PaperProjectBridge` 接收 working copy，写作模块消费 package/evidence refs 并通过 feedback/recheck event 回传问题。
- D120: 跨模块只传 ref、snapshot、bridge 和 working copy，不共享可变内部状态；每个 bridge 必须保存 source refs、target refs、snapshot hash、working-copy payload hash 和 artifact refs。
- D121: 横向人机职责模型采用 draft_only、agent_actionable、human_confirmed、human_override_only 四级权限；LLM/agent 可生成建议和低风险动作，但责任性确认和 blocker override 必须由人完成。
- D122: `human_confirmed` 是正常流程 gate，例如确认 TopicSeed 约束、创建 ValidatedNeed、PromotionDecision.promote；`human_override_only` 是异常 gate，用于覆盖 deterministic blocker，必须记录 risk、scope、expiry/recheck condition 和 override ref。
- D123: `HumanConfirmedDecision` 和 `HumanOverride` 必须进入本地 DB；override 不修复 blocker，只允许限定范围内继续，并必须进入后续 workflow input 的 `accepted_risks`。
- D124: LLM workflow 结果必须作为 versioned `LLMWorkflowRun` 持久化，保存 workflow/prompt/model/tool versions、input snapshot、output refs、state signals、assumption/evidence summaries、human review triggers 和 artifact refs；不能只把最终文本嵌入业务对象。
- D125: multi-agent workflow 必须保存 `AgentReviewSession`；DB 保存 roles、protocol、round count、accepted/unresolved objection summary、human triggers 和 transcript artifact refs，完整 prompt/response/transcript 进入 artifact store。
- D126: PromptTemplateVersion、ModelProfile、LLMWorkflowOutputRef 和 WorkflowQualityFeedback 应进入本地 DB；human reject、override、recheck invalidation、downstream failure、accepted outcome 和 rerun instability 都应反馈到 workflow quality。
- D127: LLM raw hidden reasoning / chain-of-thought、provider secrets、transient token stream、未引用 scratchpad 和未经授权的外部全文不持久化；full prompt/response、raw JSON output、long memos、tool outputs 和 rerun diff report 进入 artifact store 并保存 checksum refs。
- D128: 持久化实现采用 P0-P3 schema roadmap：P0 先落 core identity/version/trace，P1 落正式 decision objects，P2 落 cross-cutting control，P3 用 thin record + JSON payload + artifact refs 过渡并按查询/recheck 需求拆表。
- D129: P0 独立表优先包括 TopicSeed、SearchPlan、SearchRun、EvidenceMap、EvidenceUnit、FunctionalLineageLink、TraceSnapshot、ArtifactRef、LLMWorkflowRun；P1 包括 NeedCandidate、ValidateNeedAdjudicationResult、ValidatedNeed、ResearchSlice、TopicQuestion、TopicValueAssessment、ValueDispositionDecision、TopicPackage、PromotionDecision、PaperProjectBridge。
- D130: P2 独立表优先包括 TransitionPolicyVersion、ChainTransitionAttempt、ReadinessGateResult、AcceptedRisk、RecheckEvent、RecheckImpact、RecheckResolution、HumanConfirmedDecision、HumanOverride、AgentReviewSession、WorkflowQualityFeedback；P3 包括 SeedDiscoveryRun/SeedCandidate、option/candidate sets、TypedLink/Cluster/Pattern/ConflictSet、PromptTemplateVersion、ModelProfile、LLMWorkflowOutputRef 等可逐步细化对象。
- D131: 字段列化规则：identity、state axes、version、supersession、source refs、workflow_run_id、snapshot_hash、artifact_refs、evidence_unit_id、impact_level、recheck flag、human trigger、accepted risk、decision type、loopback target 和 required actions 不能只放 JSON。
- D132: 横向 readiness/quality gate 采用 BuildInputSnapshot -> DeterministicGate -> LLMReadinessAssessment -> HumanGate(if required/escalated) -> GateDecision；hard blocker 优先于评分。
- D133: `ReadinessGateResult` 必须进入本地 DB，保存 result、hard blockers、warnings、required actions、loopback target、human_review_required、accepted risk refs、evidence refs、functional refs、workflow_run_id 和 decided_by。
- D134: `pass_with_risk` 必须绑定 accepted_risk_refs；`blocked/needs_revision` 必须带 loopback_target 和 required_actions；gate 失败可触发 RecheckEvent、upstream revision request、park 或 reject。
- D135: 节点级最低 gate 统一覆盖 seed intent/constraints、SearchPlan coverage、SearchRun accounting、EvidenceMap claim-level evidence、Need validation readiness、slice boundary/resource trace、question answerability、value reasoning completeness、package trace/boundary 和 promotion blocker。
- D136: 完整选题链路是目标架构，不是 v1 一次性实现范围；v1 应优先验证 `TopicSeed -> SearchPlan -> SearchRun -> EvidenceMap/EvidenceUnit -> NeedCandidate -> ValidateNeedAdjudicationResult -> ValidatedNeed` 的 evidence-to-need 质量闭环。
- D137: 工程复杂度控制要求 P0/P1 先支持 identity、version、trace、gate 和最小 UI，P3 对象先用 thin record + JSON payload + artifact refs，避免一次性完整表化所有对象。
- D138: UI v1 应优先 reviewer cards、gate blockers、trace drilldown 和 recheck queue，不做复杂全图工作台；recheck v1 先局部/手动/半自动，不默认全链 storm propagation。
- D139: multi-agent review 不作为所有节点默认流程，只在高风险、高不确定性、强分歧、rerun instability 或 high-impact gate 中触发；每个实现拆分必须验证明确质量假设。
- D140: `TopicValueAssessment` 内部拆分为 `ValueReasoningMemo` 和 `ValueDispositionDecision`；前者是 LLM/agent 可生成的价值论证材料，后者才是正式价值处置对象。
- D141: value 阶段不使用 `promote`，避免与 `PromotionDecision.promote` 混淆；正式 value disposition 使用 `advance_to_package/refine_question/refine_slice/park/drop`。
- D142: `TopicPackage(draft)` 只从 `ValueDispositionDecision.decision = advance_to_package` 创建；`ValueReasoningMemo` 的 recommendation 不直接触发 package 创建或状态转移。
- D143: `SearchPlanCoverageMatrix` 是 `SearchPlan.version` 下的一等 reviewer-facing 聚合视图，不是自然语言备注，也不是单表多方覆盖写入的事实源；权威数据由 coverage intent、execution observation、evidence binding、assessment 和 risk acceptance 五层 child records 组成。
- D144: `CoverageMatrix` 分层写入：SearchPlan workflow 写 `CoverageRowIntent`，SearchRun 写 `CoverageExecutionObservation`，EvidenceMap 写 `CoverageEvidenceBinding`，AssessCoverage 写 `CoverageAssessment`，human gate/workspace policy 写 `CoverageRiskAcceptance`；下游 gate 读取 assessment + risk acceptance，不读取自然语言 matrix summary。
- D145: `EvidenceStrengthAssessment` 是 target-specific 但 demand-driven 的证据强度评估，不是 paper quality score 或 EvidenceMap 总分；同一 EvidenceUnit 对不同 NeedCandidate、ValidationDecisionSupportPacket、ValidatedNeed、ResearchSlice、TopicQuestion、TopicQuestionContract、TopicValueAssessment、ValueDispositionDecision、TopicPackage、PromotionDecision 或 PromotionGateCheck target 可以有不同 support/challenge/baseline 强度，但不得全量预计算笛卡尔积。
- D146: `EvidenceStrengthAssessment` 不产生新事实，只评估既有 EvidenceUnit/Cluster/TypedLink/evidence bundle 在目标判断中的可用性；必须保留 target_ref、role、strength、directness、scope_fit、conflict_level、usable_for_gate、confidence、workflow_run_id、granularity、purpose 和 recheck 状态，并被 Need readiness、ValidatedNeed adjudication、slice/question/value/promotion gate 消费。
- D146a: `EvidenceStrengthAssessment` 触发必须区分 readiness、adjudication、challenge、contract、promotion、human-review 和 recheck；SearchRun 完成或普通 EvidenceUnit 新增不自动触发全 target reassessment。
- D146b: `EvidenceStrengthAssessment` 复用必须依赖 target type/id/version、purpose、granularity、evidence bundle hash、EvidenceMap version、SearchPlan/SearchRun refs、policy version 和 workflow version 组成的 cache key；不得跨 target 语义复用。
- D146c: `EvidenceStrengthAssessment` 在证据 claim/locator/source health/rights/dedup/extraction、target version、strong baseline/counter-evidence/conflict、high-priority coverage assessment、workflow bug 或 human challenge 变化时进入 stale/recheck_required。
- D147: `NeedCandidate.unmet_mechanism` 采用结构化字段 + 受约束 narrative 的混合形式，用于解释现有方案为什么在特定边界下仍不足；它是 evidence-backed hypothesis，不是事实，narrative 不能引入结构化字段和 evidence refs 之外的新事实。
- D148: `unmet_mechanism` 的赋值采用 workflow 分权：GenerateNeedCandidates 生成草案，EvidenceGroundingReviewer 检查引用，SkepticChallenge/BaselineCritic 挑战伪 gap 或已解决机制，AssessCandidateReadiness 阻断不清晰机制，ValidateNeedAdjudication + human confirmation 冻结 accepted mechanism snapshot。
- D149: `ResearchSlice.slice_budget` 是 slice 选择阶段的可行边界和 claim ceiling 约束，不是 PaperProject 执行排期；它覆盖时间、算力、数据、标注、baseline reproduction、实现、评测复杂度、dependency risk、budget blocker 和 feasible claim ceiling。
- D150: `slice_budget` 由 ResearchConstraintProfile 提供资源边界，PlanResearchSlice 估算每个 option，FeasibilityCritic 挑战低估，SliceSelectionDecision 将 budget fit 纳入 hard gate/comparative fit，只有高资源风险、强 claim 依赖重资源或需要接受预算风险时升级人审。
- D151: `TopicQuestionContract` 是 `TopicQuestion` 的版本化 child record，不是新的链路节点；它在 `SelectTopicQuestion` 准入后固化问题核心、边界、需求继承、claim 上限、answerability route、证据/假设引用、资源约束和下游使用合同。
- D152: `QuestionContract` 的数据来源必须限制为冻结上游引用：ResearchSlice.version、准入 TopicQuestionCandidate、TopicQuestionSelectionDecision、Need/Evidence/Boundary/Assumption refs、EvidenceStrengthAssessment、ResearchConstraintProfile 和 FormTopicQuestionRun input snapshot；未准入候选、LLM 新背景、全文论文和下游 value/package 判断不能反向成为 contract 来源。
- D153: `QuestionContract` 一旦被 `TopicValueAssessment` 消费，不得原地覆盖；边界、claim strength、evaluation route、source refs 或 answerability dependency 实质变化时创建新 contract version，并把旧 assessment 标记 `recheck_required`。
- D154: `TopicQuestionFalsificationCondition` 是 contract 的结构化子记录，用于表达 hard、soft/degradation 和 answerability 失败条件；它不是普通风险清单，触发后产生 recheck/disposition/loopback，由对应 workflow 决定 revise、lower claim、park 或 drop。
- D155: `PromotionCommitmentProfile` 是 `PromotionDecision` 的子对象，不是新的主链节点；它记录 promotion 时人类确认的 scope、claim ceiling、non-negotiable boundaries、allowed refinements、accepted risks、required conditions、early checks 和 stop/reopen conditions。
- D156: `PromotionCommitmentProfile` 不重新评估 value，也不替代 PaperProject plan；LLM 可生成草案和检查 blocker，但 profile 必须由 HumanPromotionDecision 确认后生效，并由 PaperProjectBridge 作为下游交接快照。
- D157: 状态模型必须拆成正交状态轴，而不是用单个 `status` 同时承载 lifecycle、decision、review、freshness、execution 和 permission 语义；新表应优先列化 `lifecycle_status`、`decision_status`、`review_status`、`freshness_status`、`execution_status` 和 `permission_status`。
- D158: `RecheckEvent/RecheckImpact` 只更新 freshness/impact 语义，不改写历史 decision；例如 `ValidatedNeed` 可以同时保持 `decision_status=accepted`、`review_status=human_confirmed`，并因新证据进入 `freshness_status=recheck_required`。
- D159: blocker 必须先经 `BlockerPolicy` 分类为 `non_overridable`、`overrideable_with_risk` 或 `escalation_only`；trace/ref/schema/legal/auth、新未验证 need、不可接受边界越界、绕过 promotion 人审等 blocker 不可 override，只能修复、回退、重跑或创建新合法对象。
- D160: coverage/resource/confidence/secondary-evidence blocker 可以由人带风险继续，但必须创建 `HumanOverride` 和 accepted risk；strong counter-evidence、claim overreach、answerability unclear、slice budget high risk、promotion commitment conflict 等 blocker 必须升级人审或 focused review，agent 不得自动通过。
- D161: `SearchPlan` v1 不需要独立全屏 UI；先作为 title-card/reviewer workbench 内的 plan panel、coverage matrix、blocker/recheck 卡片和 trace drilldown 呈现。独立 UI 只有在审查负载证明必要时再拆。
- D162: `TopicValueAssessment` 的边界收紧为判断当前 `QuestionContract` 在当前证据、资源和约束下是否值得进入 `TopicPackage(draft)`；它不判断“论文一定能发表”，也不把 `publishable` 作为简单布尔 gate。
- D163: `publishability` 应作为 value reasoning 中的可辩护最低贡献形态来论证，例如 `minimum_defensible_contribution_claim`、claim leverage、reviewer risk、community fit 和 effort-to-value fit；hard gate 只阻断 answerability 不成立、strong baseline 已解决、fallback claim 不可执行、证据断裂或 claim strength 超出 evidence/slice_budget 等情况。
- D164: promotion 到 `PaperProject` 前不额外强制 research-argument readiness gate；选题侧必经 gate 是 `PromotionDecision`，`TopicPackage`、`PromotionCommitmentProfile` 和 `PaperProjectBridge` 负责交接 trace、conditions 和 early checks，下游 research-argument/writing 模块通过 feedback/recheck event 回传问题。
- D165: `LiteratureResourcePoolSnapshot` 是文献模块 owned 的 derived read model 和选题链输入边界；v1 可由现有 literature repository、auto-pull suggestions、imported records 和人工导入聚合生成，不必先作为新的 canonical 写模型，但 `SearchPlan` / `SeedDiscoveryRun` / `SearchRun` 必须消费具体 snapshot id 和 provenance。
- D166: `advance_to_package` 只表示创建 draft handoff package；promotion-ready 或 PaperProject 创建授权只能来自 package readiness 检查后的显式 `PromotionDecision` 路径，其中 `promote/promote_with_conditions` 必须 human-confirmed。
- D167: 统一控制面定义为 `DecisionChainControlPlane`：语义上是 runtime kernel，负责 transition entrypoint、TransitionPolicy、ReadinessGateResult、state-axis writes、human gate、override、recheck event 和 audit trail；实现上 v1 采用 harness-first，不做完整 long-running runtime。
- D168: `WorkflowHarness` 只负责执行节点级 LLM/agent workflow，并产出 `LLMWorkflowRun`、structured output、artifact refs、state_signals、human_review_triggers 和 recommendation；它不能直接写权威状态、创建 human-confirmed 对象、dismiss blocker 或绕过 TransitionPolicy。
- D169: 所有关键推进都必须通过 `attemptTransition(transition_key, source_ref, actor, requested_inputs)`，标准流程为 BuildInputStateContext -> DeterministicGate -> WorkflowHarness(if needed) -> ReadinessGateResult -> TransitionPolicyDecision -> HumanGate/OverridePolicy -> StateWriter -> RecheckCoordinator。
- D170: v1 不实现完整 runtime 能力：暂不做自动多节点调度、优先级队列、取消/恢复、并发锁、自动重试和全链 recheck storm propagation；recheck 先记录事件和局部队列，由人或明确操作触发处理。
- D171: 控制面 v1 必须持久化 `TransitionPolicyVersion` 和 `ChainTransitionAttempt`，并把 `policy_version_id/gate_result_id/workflow_run_id/human_decision_id/override_id/recheck_event_refs` 写入 transition audit，确保后续能解释每次通过、阻断、回流、park、reject 或人审排队。
- D172: 实施范围硬切为 v1a/v1b/v1c：v1a 验证 `TopicSeed -> SearchPlan -> SearchRun -> EvidenceMap/EvidenceUnit -> NeedCandidate -> ValidateNeedAdjudicationResult -> ValidatedNeed` 的 evidence-to-need 质量闭环；v1b 扩展到 ResearchSlice/TopicQuestion/TopicValueAssessment/TopicPackage(draft)；v1c 扩展到 PromotionDecision/PaperProjectBridge。
- D173: v1a 的终点是 `ValidatedNeed`，且必须包含 human confirmation；不要把 `ResearchSlice` 提前设为 v1a 必经 active gate，以免混淆“需求是否真实”和“如何做成题”。
- D174: v1a authority tables 包括 TopicSeed、LiteratureResourcePoolSnapshot、SearchPlan、coverage child records、SearchRun、EvidenceMap/EvidenceUnit、NeedCandidate、CandidateDecisionMemory、ValidationDecisionSupportPacket、ValidateNeedAdjudicationResult、ValidatedNeed、ReadinessGateResult、LLMWorkflowRun、ChainTransitionAttempt、HumanConfirmedDecision 和最小 AcceptedRisk。
- D175: v1a thin persisted records 包括 SeedDiscoveryRun、SeedCandidate、EvidenceStrengthAssessment、SearchPlanRecheckRequest、RecheckEvent/RecheckImpact、HumanOverride 和 AgentReviewSession；它们保留稳定 ID、关键状态、refs、payload 和 artifact refs，但不在 v1a 完整拆表或成为所有 gate 强依赖。
- D176: ResearchSlice、ResearchSliceOptionSet、SliceSelectionDecision、TopicQuestion、TopicQuestionContract、TopicValueAssessment、ValueDispositionDecision、TopicPackage、PromotionDecision 和 PaperProjectBridge 只保留目标合同，不作为 v1a 的主要 UI、自动推进对象或必经 gate。
- D177: v1b 定义为 Need-to-Draft-Topic，入口是 human-confirmed ValidatedNeed、可追溯 EvidenceMap/SearchPlan/SearchRun 版本、无未处理 high-priority recheck 或已有 AcceptedRisk，以及轻量 ResearchConstraintProfile；成功出口是 `TopicPackage(draft)`。
- D178: v1b authority/gate objects 包括 ResearchSlice、SliceSelectionDecision、TopicQuestion、TopicQuestionContract、TopicValueAssessment、ValueDispositionDecision、TopicPackage(draft)、ReadinessGateResult、ChainTransitionAttempt 和 AcceptedRisk；support objects 包括 PlanResearchSliceRun、ResearchSliceOptionSet/Option、SliceSelectionReviewSession、FormTopicQuestionRun、TopicQuestionCandidateSet/Candidate、TopicQuestionSelectionDecision、QuestionFormationReviewSession 和 ValueReasoningMemo。
- D179: v1c 定义为 DraftPackage-to-PaperProjectBridge，入口是 trace/boundary check 通过且风险可见的 TopicPackage(draft)；主链为 PromotionDecisionSupport -> PromotionGateCheck -> HumanPromotionDecision -> PromotionDecision -> PromotionCommitmentProfile -> PaperProjectBridge。
- D180: v1c 只有在 `PromotionDecision.decision = promote | promote_with_conditions` 时创建或连接 PaperProjectBridge；完整 PaperProject execution plan、写作 agent、实验执行计划自动化和 research argument workspace 不属于 v1c。
- D181: v1a/v1b/v1c 综合覆盖当前选题管理链路和论文管理回溯选题管理的功能目标；但不覆盖完整论文执行自动化，且实现前仍需继续收口 CoverageMatrix 分层、AcceptedRisk、LiteratureResourcePoolSnapshot、EvidenceStrengthAssessment 触发策略、recheck storm 防护、人审 UI、negative memory 复用和 offline evaluation / replay harness。
- D182: `CoverageRiskAcceptance` 不独立表达风险事实，必须引用统一 `AcceptedRisk` 对象；coverage gap 的人类接受、pass_with_risk 和 override risk 需要进入同一风险接受模型。
- D183: `AcceptedRisk` 是统一风险接受对象，覆盖 `pass_with_risk`、`HumanOverride`、`CoverageRiskAcceptance`、`ValueDispositionDecision.accepted_risk_refs`、`PromotionCommitmentProfile.accepted_risk_refs`、promotion conditions 和 recheck dismiss/defer with risk；它不是 evidence，也不是 blocker resolution。
- D184: `HumanOverride` 是覆盖 blocker 的动作，`AcceptedRisk` 是接受残余风险的记录；HumanOverride 必须创建或引用 AcceptedRisk，但 AcceptedRisk 不一定来自 HumanOverride。
- D185: 每个 `AcceptedRisk` 必须记录 source ref、risk type、severity、accepted_by、scope、rationale、affected object refs、affected transitions、downstream visibility、expiry/recheck condition 和 active/expired/resolved/superseded status；无 scope 或 expiry/recheck condition 的风险接受无效。
- D186: `BuildInputStateContext` 必须向下游 workflow 暴露 relevant active accepted risks；LLM/agent 必须显式处理这些风险，不能把 accepted risk 当作 blocker 已解决，也不能把 accepted risk 当作支持 need/value 的 evidence。
- D187: `LiteratureResourcePoolSnapshot` 的数据来源包括 library records、manual import、import/auto-pull batches、bibliographic metadata、fulltext/OCR/section extraction versions、tags/collections/manual notes、embedding/citation clusters、dedup/canonical source maps、source health 和 workspace filter policy。
- D188: `LiteratureResourcePoolSnapshot` 的主要消费方是 SeedDiscoveryRun、SearchPlan、SearchRun、EvidenceMap/EvidenceUnit builder、AssessCoverage/CoverageMatrix、NeedCandidate/ValidateNeedAdjudication 和 UI/audit/rerun；选题模块不得用 live resource pool 替代被记录的 snapshot。
- D189: `LiteratureResourcePoolSnapshot` v1a 必须持久化 snapshot id、workspace/title-card scope、source_pool_version、library_index_version、filter policy、included/excluded source refs、batch refs、dedup/canonical map versions、source health summary、fulltext availability summary、snapshot_hash 和 artifact refs；大体量列表/diagnostics 可进入 artifact store。
- D190: snapshot 不原地修改；资源池、索引、dedup、source health、filter policy 或 extraction version 变化时创建新 snapshot。被正式 workflow 消费的 snapshot 即使是临时 read model，也必须 materialize 或保存 hash + materialized refs。
- D191: 新 snapshot 只有在高相关新文献、source health 变化、dedup/canonical map 改变、fulltext extraction 变化、filter policy 改变或 auto-pull/import batch 命中 active SearchPlan coverage gap 时触发 recheck review；它不自动作废旧 SearchPlan。
- D192: R8 作为横向机制处理：v1a 使用 on-demand bundle-level `EvidenceStrengthAssessment` 支撑 NeedCandidate readiness、ValidateNeedAdjudication、coverage blocker、challenge/conflict set 和人审请求；不对所有 EvidenceUnit 预计算。
- D193: v1b 将 `EvidenceStrengthAssessment` 扩展为 contract-level bundle assessment，用于 ResearchSlice boundary、TopicQuestionContract answerability/trace、TopicValueAssessment evidence sanity 和 claim strength 检查；只对 selected/admitted objects 触发，不全量评估未准入候选。
- D194: v1c 默认消费已有 evidence strength assessments，并只在 PromotionGate blocker、人审质疑、assessment stale/recheck_required、accepted risk expiry 或 package narrative 与证据强度冲突时运行 focused reassessment；v1c reassessment 不反向改写历史判断，只触发 recheck 或新版本。
- D195: R10 recheck 采用 `Recheck ledger, not recheck automation`：`RecheckEvent` 记录变化，`RecheckImpact` 限定受影响对象和影响等级，`RecheckResolution` 记录关闭方式；v1a 不做自动级联、后台 scheduler、全 workspace 扫描或自动重跑。
- D196: LLM/workflow 只能输出 `state_signals` 和影响建议；只有控制面中的 `RecheckCoordinator` + `StateWriter` 可以通过 `RecheckImpact/RecheckResolution` 写入权威 `freshness_status`。
- D197: 防 recheck storm 的最小机制包括 `event_fingerprint`、`impact_dedup_key`、cooldown、batch event、retry budget、stop condition 和 lineage/ref-limited propagation；二级传播必须由新的 impact assessment 或关键 gate 触发。
- D197a: `RecheckEvent` 准入必须严格：只有跨对象影响、关键 transition blocker、人审/override 需求、durable memory 价值或 downstream feedback 创建正式 event；local warning、重复 signal 和 search noise 应合并或 audit-only。
- D197b: recheck rerun 必须有新 information 条件，例如新 evidence/source、SearchPlan/EvidenceMap/target version、policy/workflow version、accepted-risk condition 或 explicit human instruction；cooldown 到期只允许重新评估，不自动重跑。
- D197c: storm-control decision 必须可审计，记录 batch、merge、downgrade、delay、stop、supersede 或 escalate human review 的理由与 refs。
- D198: `RecheckImpact.impact_level` 固定为 `no_impact/stale/recheck_required/invalidated`。`stale` 是提示和刷新需求，`recheck_required` 阻断关键 transition，`invalidated` 必须进入 retract/supersede/drop/revise 等节点语义处理，不能简单 dismiss。
- D199: `AcceptedRisk` 不因任意 recheck event 自动失效；只有 expiry/recheck condition 命中、新证据超出原 accepted scope、severity 升级或 human/gate 明确要求时，才重新打开或要求 downstream 重新处理。
- D200: `RecheckEvent` / `RecheckImpact` / `RecheckResolution` 不按 v1a/v1b/v1c 拆分对象模型；阶段差异通过 `origin_stage`、`affected_stage`、`handling_profile`、`policy_version_id`、`blocks_transition_keys` 和 affected object set 表达。
- D201: v1a 的 recheck profile 限定为 `evidence_to_need_lightweight`，主要影响 SearchPlan/SearchRun/EvidenceMap/EvidenceUnit/NeedCandidate/ValidatedNeed；v1b 扩展到 ResearchSlice/TopicQuestion/TopicValueAssessment/TopicPackage(draft)；v1c 扩展到 PromotionDecision/PromotionCommitmentProfile/PaperProjectBridge 和 downstream feedback。
- D202: downstream 模块回传问题使用同一套 recheck 模型，`origin_stage = downstream`，通过 `affected_stage` 指向需要复查的选题阶段；已经 bridge 到 PaperProject 的内容不得反向覆盖 upstream authority，只能创建 feedback/recheck event、新版本或 human-confirmed follow-up。
- D203: UI 框架在现有 desktop shell 和 `data-ui` / token / contract 约束上定义，不为选题链路创建独立视觉体系或全新导航体系；新 UI 不得扩展 frozen legacy compatibility layer。
- D204: 选题链路 UI 采用 title-card reviewer workbench，而不是全链路大图或每个对象一个主页面。框架分为 App Shell / Navigation、Workspace / Title-card Workbench、Decision Review Surfaces、Queue Surfaces、Trace / Evidence Drilldown、Settings / Policy Surfaces。
- D205: Decision Review Surfaces 承载 human-confirmed、高风险 agent decision 和 escalated review；必须展示确认范围、证据、反证、blocker、accepted risk、required action 和 downstream effect，不能用单一 score 或推荐按钮替代研究判断。
- D206: Queue Surfaces 只处理 focused work queues，包括 human review、recheck、blocker、accepted risk expiry 和 failed/partial workflows；队列项必须回到 decision review 或 trace drilldown，不把队列做成主叙事界面。
- D207: Trace / Evidence Drilldown 按需展开 EvidenceUnit/ContentRef、FunctionalLineageLink、SearchRun、LLMWorkflowRun、RecheckEvent/Impact/Resolution、HumanConfirmedDecision/HumanOverride/AcceptedRisk；它解释来源和审计，不替代决策摘要。
- D208: Negative memory 统一定义为 `DecisionMemoryEntry`，是失败理由和历史处置理由的可复用上下文层；v1a 可先以 `CandidateDecisionMemory` 作为 evidence-to-need 阶段投影。
- D209: Decision memory 的赋值采用 `LLM proposes -> Gate normalizes/checks -> Human confirms when high impact or ambiguous -> Control plane persists`；LLM 输出不能直接成为权威 memory。
- D210: LLM 可提出 `memory_type`、`normalized_statement`、`applicability_scope`、`severity`、`confidence`、`effect_policy_suggestion`、`retrieval_keys` 和候选 refs；系统派生 source decision/stage、target scope、workflow run、duplicate group、初始 status；gate/human 决定最终 effect_policy、accepted scope、expiry/recheck condition 和 status changes。
- D211: Decision memory 不是 EvidenceUnit，不能直接作为事实证据或创新阻断理由；它必须有 scope、source refs、recheck condition 和 effect_policy，只有 scope 匹配且 `effect_policy = block_until_rechecked` 时才阻断关键 transition。
- D212: Decision memory 的来源包括 rejected/parked/merged NeedCandidate、ValidateNeedAdjudication 失败、SliceSelectionDecision 失败、TopicQuestionSelectionDecision 失败、TopicValueAssessment park/drop/refine、PromotionDecision blocker、downstream failure、recheck invalidation、human reject、accepted risk expiry 和 workflow instability。
- D213: Decision memory 必须进入 GenerateNeedCandidates、AssessCandidateReadiness、ValidateNeedAdjudication、PlanResearchSlice、FormTopicQuestion、TopicValueAssessment 和 PromotionGateCheck 的输入上下文；消费方式是 warning、required challenge、blocker 或 recheck stale/supersession，而不是直接删除新方向。
- D214: `QualitySignal` 收缩为 runtime gate/routing 质量信号，不做面向人的审查报告、复杂 rubric、offline evaluation 或 v1 全链路 dashboard；人类只看 gate 汇总后的结果、blocker、required action 和 accepted risk。
- D215: `QualitySignal` 不是 evidence，也不直接改状态；它由 ReadinessGateService、TransitionPolicy、RecheckCoordinator、DecisionMemoryEntry 生成流程和 downstream workflow input context 消费。
- D216: `QualitySignal` 至少保存 target_ref、stage、check_type、verdict、issue_codes、recommended_action、blocking_transition_keys、evidence/functional/recheck/memory refs、confidence、workflow_run_id、artifact_refs 和 created_at。
- D217: v1a 的 `QualitySignal` check_type 限定为 evidence_grounding、searchplan_coverage、pseudo_gap_risk、already_solved_risk、trace_integrity 和 workflow_stability，先服务 evidence-to-need 质量闭环。
- D218: 整体调度器不得直接解释 raw `QualitySignal`；控制面必须先通过 TransitionPolicy 将 signal 派生为 ReadinessGateResult、RecheckImpact、DecisionMemoryEntry candidate、QueueItem/RequiredAction 或 ChainTransitionAttempt，调度器只消费这些派生记录。
- D219: `QualitySignal.recommended_action` 是质量建议，不是执行计划；同一 signal 在不同 transition policy 下可能只是 warning，也可能阻断、触发 recheck、进入人审或生成 decision memory。
- D220: LLM workflow complexity 由 `WorkflowProfilePolicy` 控制，profile 升级路径为 `basic -> focused_critic -> full_debate -> human_review`；multi-agent 不是默认配置。
- D221: profile 触发来源包括 deterministic gate、QualitySignal、DecisionMemoryEntry、evidence/coverage 条件、workflow 自身低置信/分歧信号、transition importance 和 explicit human request；触发规则写在 TransitionPolicy/WorkflowProfilePolicy，不写死在 prompt。
- D222: `DecisionChainControlPlane` 负责选择 workflow profile；LLM 只能输出 `profile_escalation_suggestion`，不能自行升级为 full debate、绕过 policy 或推进状态。
- D223: `WorkflowHarness` 启动已选择的 workflow run，`AgentOrchestrator` 只负责编排单次 run 内部的 roles、rounds、并行/串行、critic 顺序、timeout、token/cost 上限和 synthesis；它不写业务状态。
- D224: 全局 scheduler 只启动控制面已确定的 workflow job；不得直接解释 `QualitySignal`，也不得独立拉起 multi-agent debate。
- D225: v1a profile 规则：GenerateNeedCandidates 默认 basic + optional skeptic；AssessCandidateReadiness 默认可用 focused_critic；ValidateNeedAdjudication 使用 focused_critic + human confirmation；full_debate 只在 high uncertainty、strong challenge、already_solved risk 或高影响 validated decision 前由 policy 触发。
- D226: 同一 input snapshot 不允许无限 rerun；每个 workflow profile 必须定义 max rounds、retry budget、stop condition、output contract、升级条件和 artifact 保存策略。full debate 的 synthesis 必须保留 accepted/unresolved objections、minority blocker 和 required actions，不能简化为投票结果。
- D227: `ResearchConstraintProfile` 是 v1b 的入口约束快照，不是项目排期或完整实验计划；它限制 ResearchSlice、TopicQuestion、TopicValueAssessment 和 TopicPackage(draft) 的可行边界。
- D228: v1b 最小 `ResearchConstraintProfile` 必须包含 time/resource boundary、data availability、baseline reproduction expectation、contribution preference、target community、non-goals 和 unknowns。
- D229: `ResearchConstraintProfile` 的来源包括用户显式约束、workspace 默认值、v1a 继承的 AcceptedRisk/SearchPlan coverage gap/ValidatedNeed scope/EvidenceMap resource notes，以及 LLM 整理出的 unknowns；LLM 不能虚构资源、数据、外部访问或用户实验许可。
- D230: `ResearchConstraintProfile` 一旦被 ResearchSlice 或 TopicQuestion 消费不得原地覆盖；约束实质变化创建新 version/snapshot，并使下游 ResearchSlice/TopicQuestion/TopicValueAssessment recheck_required 或创建新版本。
- D231: v1c 定义为 DraftPackage-to-PaperProjectBridge；它是从 `TopicPackage(draft)` 到 `PaperProjectBridge` 的授权桥接层，不重新评估 topic value，也不启动完整 PaperProject execution。
- D232: v1c 入口必须包含通过 trace/boundary check 的 `TopicPackage(draft)`、可追溯的 TopicQuestion/QuestionContract/ResearchSlice/ValidatedNeed/selected evidence refs、可见 AcceptedRisk/open blockers/promotion conditions、已处理或明确阻断的 RecheckImpact，以及不冲突的 ResearchConstraintProfile。
