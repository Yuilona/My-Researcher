## Durable Notes
- The task bundle exists because this redesign is multi-session and will likely feed future contract/API/DB/UI implementation work.
- `06-design-spec.md` is the canonical design artifact for this task.
- This file must not become a second design spec. If wording conflicts with `06-design-spec.md`, the design spec wins and this file should be corrected.
- No product code, schema, or API changes should be made from this task until the design and implementation roadmap are accepted.
- The old `automated_topic_notes.md` chain remains the semantic spine, but the new design is a non-linear decision system with loopbacks, review states, failure paths, and preserved negative records.
- `SearchPlan` is a formal decision object, not a parameter bag. Its implementation must represent coverage hypothesis, resource-pool assessment, risk register, stop conditions, confidence, review state, and provenance.
- auto-pull remains upstream literature supply: `LiteratureImportSettings -> auto-pull/import -> LiteratureResourcePool -> SearchPlan`.
- `LiteratureResourcePoolSnapshot` is the topic-chain input boundary for literature resources. It is owned by the literature module as a derived read model; topic-selection workflows consume snapshot refs/provenance rather than live resource-pool state.
- `SeedDiscoveryRun`, `SearchPlan`, and `SearchRun` must reference a concrete `LiteratureResourcePoolSnapshot`. Snapshot data sources include library records, import/auto-pull batches, manual imports, metadata, fulltext/extraction availability, tags/clusters, dedup/canonical maps, source health, and workspace filter policy.
- Persist `LiteratureResourcePoolSnapshot` in v1a with snapshot id, source/library/index versions, filter policy, included/excluded source refs, batch refs, dedup/canonical map versions, source health summary, fulltext availability summary, snapshot hash, and artifact refs. Do not mutate snapshots in place.
- New snapshots should trigger recheck review when high-relevance sources appear, source health changes, dedup/canonical maps change, extraction versions alter locators/claims, or filter policies change. They do not automatically invalidate old SearchPlans.
- `SearchPlan` should be persisted primarily in the local DB because downstream objects need stable version references, state-axis transitions, queries, and recheck propagation.
- `SearchPlanCoverageMatrix` should be a first-class reviewer-facing view under `SearchPlan.version`, not just narrative notes. Its authority data should be split into child records: `CoverageRowIntent`, `CoverageExecutionObservation`, `CoverageEvidenceBinding`, `CoverageAssessment`, and `CoverageRiskAcceptance`.
- Coverage writing is responsibility-layered: SearchPlan workflows write row intent, SearchRun writes execution observations, EvidenceMap writes evidence bindings, AssessCoverage writes coverage assessment, and human gate/workspace policy writes risk acceptance. Do not let multiple actors mutate the same coverage row fields directly.
- `CoverageRiskAcceptance` must reference a unified `AcceptedRisk`; it is not just a boolean accepted gap flag.
- Local files/artifacts are suitable for LLM raw outputs, long-form diagnostics, prompt/response snapshots, and exportable review bundles; DB records must keep artifact refs/checksums.
- LLM actions around SearchPlan should generate, critique, revise, explain, and diagnose coverage; they must not approve promotion or mutate auto-pull/import settings.
- `SearchRun` is execution provenance for a SearchPlan version, not the LLM reasoning result that created the plan. LLM reasoning belongs to SearchPlan artifacts; LLM calls used inside execution may be attached as SearchRun execution artifacts.
- `SearchRun` consumes SearchPlan version data plus resource-pool/search-source inputs and primarily feeds EvidenceMap construction, plan review, NeedCandidate generation, falsification, value assessment, audit/re-run, and UI inspection.
- A robust SearchRun must be reproducible and auditable: persist execution snapshots, selected/excluded/dedup/failed accounting, source health, must-check status, coverage delta, LLM execution artifacts, and re-run comparison inputs.
- EvidenceMap should be built from claim-level EvidenceUnits, not paper-level records. A paper may yield multiple units across problem, solution, limitation, evaluation, baseline, resource, assumption, and counter-evidence roles.
- EvidenceUnit exists to support topic value judgment; paper records remain source containers and bibliographic provenance.
- Claim v1 should remain embedded in EvidenceUnit as structured payload. It must separate source wording, normalized topic-facing statement, interpretation, scope, qualifiers, comparison, topic relevance dimensions, provenance, and review state.
- Claim representation should be hybrid: structured fields are the authoritative computation/review layer, while narrative fields are constrained LLM-facing corpus material derived from the structured fields and provenance.
- Claim narrative should be based on locator-backed high-value source content, not whole-paper summaries or free-form model prose.
- EvidenceUnit should group fields into identity, provenance, claim, topic linkage, quality, review, and lifecycle. Its data sources are SearchRun refs, LiteratureResourcePool provenance, locator-backed source content, LLM extraction artifacts, and human notes.
- EvidenceMap v1 should use structured lists, typed links, and clusters rather than a graph database. Summary text is a view, not authority.
- EvidenceMap pollution controls must preserve challenges/conflicts, separate source claims from inference, prevent abstract-only support, track scope/baseline/source quality, and set stale/recheck states when upstream coverage changes.
- EvidenceMap may emit evidence/coverage/map quality signals and readiness signals, but final topic value and promotion decisions belong to TopicValueAssessment/PromotionDecision.
- `EvidenceStrengthAssessment` should be target-specific but demand-driven: it evaluates how strongly EvidenceUnit/cluster/bundle refs support/challenge a NeedCandidate, ValidatedNeed, ResearchSlice, TopicQuestion, ValueAssessment, or promotion target. It does not create facts, does not score papers globally, and must keep target_ref, role, strength, directness, scope_fit, conflict_level, usable_for_gate, confidence, workflow_run_id, and recheck state queryable.
- v1a uses bundle-level EvidenceStrengthAssessment on demand for NeedCandidate readiness, ValidateNeedAdjudication, high-priority coverage blockers, strong challenge/conflict sets, and human review. Do not precompute every EvidenceUnit against every target.
- v1b extends to contract-level bundle assessment for selected ResearchSlice, TopicQuestionContract, and TopicValueAssessment input snapshots, especially boundary, answerability, claim strength, and value sanity checks.
- v1c primarily consumes existing assessments and triggers focused package/promotion reassessment only for promotion blockers, human reviewer challenge, stale/recheck_required assessment, accepted-risk expiry, or package narrative conflict.
- EvidenceMap consumers split into direct consumers (NeedCandidate, falsification, ResearchSlice, TopicQuestion, ValueAssessment, TopicPackage, UI) and indirect consumers (PromotionDecision, ResearchArgumentWorkspace, PaperProject).
- EvidenceMap refresh/recheck triggers should be modeled around upstream coverage changes, evidence-quality changes, downstream challenges, and manual reviewer actions.
- Persistence v1: authority/state/version/reference data belongs in the local DB; large LLM/raw/diagnostic/export artifacts belong in artifact storage with DB refs and checksums.
- SearchRun should be a first-class persisted DB object because EvidenceUnit provenance, UI inspection, recheck propagation, and re-run comparison depend on stable run identity and accounting fields.
- EvidenceMap, EvidenceUnit, TypedLink, Cluster, Pattern, and ConflictSet should be persisted. Claim/summary/quality/details may start as JSON payloads if key query fields are still surfaced.
- EvidenceUnit/claim follows EvidenceMap as part of the evidence workspace, but the claim payload is stable. Frequent operations should update relationship/review/lifecycle/freshness layers rather than mutate source/provenance/claim content.
- Discard and promotion are state/reference operations: rejected/out_of_scope/superseded for discard; selected EvidenceUnit refs plus map version/snapshot for promotion.
- NeedCandidate is the direction-extraction layer from EvidenceMap: it represents potential unmet-need hypotheses, not adjudicated needs.
- NeedCandidate should be persisted as a DB object because it is a durable LLM reasoning/review workspace, not a transient draft artifact.
- NeedCandidate preserves candidate generation rationale, support/challenge refs, merge/reject/park history, and negative memory for future deduplication and falsification.
- NeedCandidate generation should be evidence-constrained, not brainstorm-driven. It must bind signals from EvidenceMap, prior-art/negative-memory checks, scope carving, pseudo-gap critique, and required rechecks.
- `NeedCandidate.unmet_mechanism` should use structured fields plus constrained narrative. LLM workflows may draft it, grounding reviewers check refs and narrative discipline, skeptics/baseline critics challenge already-solved or pseudo-gap mechanisms, `AssessCandidateReadiness` blocks unclear mechanisms, and `ValidateNeedAdjudication` plus human confirmation freezes the accepted mechanism snapshot.
- Rejected, partially solved, falsified, merged, parked, validated, or retracted candidate outcomes should become `CandidateDecisionMemory` for future generation and skepticism. This memory is context, not evidence, and must cite source refs.
- Treat target-architecture decision memory as `DecisionMemoryEntry`; v1a may implement `CandidateDecisionMemory` as the evidence-to-need projection. The assignment flow is LLM proposes, deterministic gate normalizes/checks, human confirms only for high-impact or ambiguous entries, and the control plane persists.
- Split decision-memory fields by authority: LLM may propose memory_type, normalized_statement, applicability_scope, severity, confidence, effect_policy_suggestion, retrieval_keys, and candidate refs; the system derives source_decision_ref, source_stage, target_scope, workflow_run_id, duplicate_group_id, initial status, and created_at; gate/human decides final effect_policy, accepted_scope, expiry/recheck_condition, and status changes.
- Decision memory must not become evidence or an innovation suppressor. It requires scope, source refs, recheck conditions, and effect_policy; only scoped `block_until_rechecked` entries can block critical transitions.
- Replace heavyweight system-evaluation reports with lightweight `QualitySignal` records. Signals are machine-readable inputs for gates, recheck, decision memory, and workflow context; they are not human review reports and not evidence.
- `QualitySignal` should keep target_ref, stage, check_type, verdict, issue_codes, recommended_action, blocking_transition_keys, refs, confidence, workflow_run_id, and artifact_refs queryable. v1a only needs evidence_grounding, searchplan_coverage, pseudo_gap_risk, already_solved_risk, trace_integrity, and workflow_stability checks.
- The scheduler must not interpret raw QualitySignal. DecisionChainControlPlane interprets signals through TransitionPolicy and may create ReadinessGateResult, RecheckImpact, DecisionMemoryEntry candidate, QueueItem/RequiredAction, or ChainTransitionAttempt; schedulers consume those derived records.
- Candidate-to-ValidatedNeed is iterative. Candidates may trigger EvidenceMap recheck or SearchPlanRecheckRequest, then create a new candidate iteration before becoming ready_for_validation.
- NeedCandidate should not mutate SearchPlan directly; it raises structured recheck requests that SearchPlan review can accept/reject/resolve.
- `ProposeSearchPlanRevision` should convert candidate/validation coverage gaps into proposed SearchPlan diffs and recommended SearchRuns, gated by reviewer acceptance.
- NeedCandidate robustness depends on stable LLM workflow design and whether SearchPlan revision loops actually enrich EvidenceMap or force rejection/parking.
- NeedCandidate ranking is not durable truth; store ranking snapshots only. ValidatedNeed should be a separate object referencing source candidate, not an in-place rename.
- `ready_for_validation` is a gate for adjudication readiness, requiring explicit support/challenge/coverage/scope/pseudo-gap assessment and no open high-priority SearchPlan recheck.
- `ready_for_validation` should be assessed by a dedicated `AssessCandidateReadiness` workflow, not majority vote. It is agent_actionable with escalation: use hard blockers, cited rationale, reviewer artifacts, and escalate human review only for high-risk/high-uncertainty/accepted-risk cases.
- `ready_for_validation -> validated` should run through `ValidateNeedAdjudication`; create a separate, human-confirmed ValidatedNeed object rather than renaming the candidate.
- `ValidateNeedAdjudication` should produce a citation-backed `ValidationDecisionSupportPacket` for human confirmation, showing strongest support, strongest challenge, coverage/open risks, and required human checks before recommendation.
- ValidatedNeed is evidence-version-bound and may later become recheck_required, challenged, superseded, or retracted when SearchPlan/EvidenceMap changes.
- ResearchSlice is the narrowing layer from ValidatedNeed to TopicQuestion. It consumes validated needs, decision support packets, EvidenceMap/provenance, decision memory, and human constraints; it outputs selected slice, included/excluded boundaries, contribution candidates, resource/baseline assumptions, rationale, and open risks.
- ValidatedNeed is necessary but insufficient for ResearchSlice. Use a `PlanResearchSlice` workflow to generate/compare `ResearchSliceOptionSet`; `SelectResearchSlice` may be agent-executed with persisted rationale/open risks, escalating to human review only for high uncertainty, strong option disagreement, resource/community conflict, or high baseline risk.
- PlanResearchSlice should use ValidatedNeedBundle, decision support packets, EvidenceMap context, SearchPlan/SearchRun provenance, CandidateDecisionMemory, and ResearchConstraintProfile to produce comparable slice options.
- `ResearchConstraintProfile` is a v1b constraint snapshot, not a project schedule or experiment plan. It should capture time/resource boundary, data availability, baseline reproduction expectation, contribution preference, target community, non-goals, and unknowns at minimum.
- ResearchConstraintProfile sources are explicit user constraints, workspace defaults, v1a inherited AcceptedRisk/SearchPlan/ValidatedNeed/EvidenceMap notes, and LLM-organized unknowns. LLM may draft the profile but must not invent resources, datasets, external access, or user-study permission.
- Constraint profile changes create a new version/snapshot rather than rewriting old plans; downstream ResearchSlice, TopicQuestion, and TopicValueAssessment become recheck_required or produce new versions when consumed constraints materially change.
- Each ResearchSliceOption must bind source needs, included/excluded boundaries, evidence alignment, baseline/resource assumptions, evaluation path, expected/fallback claim, risk profile, why_choose/why_not_choose, confidence, and human-review triggers.
- `ResearchSlice.slice_budget` is a feasibility boundary and claim-ceiling constraint, not a project schedule. PlanResearchSlice estimates it per option, FeasibilityCritic challenges underestimation, SliceSelectionDecision uses budget fit as a gate/comparison input, and the selected budget snapshot is frozen into ResearchSlice for TopicQuestion and ValueAssessment.
- PlanResearchSlice should support multi-agent debate across planner, boundary, evidence-grounding, baseline, feasibility, claim-shape, and synthesis roles. Debate is not voting; objections must cite evidence/constraints/baselines, and unresolved disagreements should become option-set warnings or human-review triggers.
- SliceSelectionDecision should be a persisted selection policy result, not a selected-option flag. It should exclude hard blockers first, then evaluate constraint/evidence/feasibility/claim/risk fit and emit select, request_more_options, park, or reject with loopback target and required actions.
- SliceSelectionDecision uses a three-layer model: hard gates determine eligibility, comparative fit compares eligible options, and synthesis decides select/request_more_options/park/reject. Do not reduce it to a single score, vote, or narrative summary.
- SelectResearchSlice should support multi-agent review over existing options. Use gate, constraint, evidence, feasibility, claim-risk, strategy, and synthesis roles; hard blockers and high-severity disagreements override majority preference.
- Persist SliceSelectionReviewSession as the review basis for SliceSelectionDecision, including per-option assessments, hard-blocker disagreements, unresolved disagreements, human-review triggers, and transcript artifact refs.
- SliceSelectionDecision must support loopback. request_more_options/park/reject require loopback_target and required_actions; even selected ResearchSlice can be looped back by TopicQuestion, TopicValueAssessment, or new evidence. Preserve old decisions and create a new decision/run/version rather than overwriting.
- Loopbacks should be exploited as planning signals: improve slice axes/options, clarify constraints, trigger EvidenceMap/SearchPlan rechecks, update decision/planning memory, and evaluate agent/prompt quality. Add retry budgets and stop conditions so loops do not repeat without new evidence, constraints, SearchPlan versions, option axes, or accepted risk.
- ResearchSlice is the versioned downstream contract produced by SliceSelectionDecision(select). It must preserve source option/selection provenance, included/excluded boundaries, claim shape, resource/data/evaluation/baseline assumptions, usage contract, and recheck/supersession state.
- Every ResearchSlice must preserve resource trace to support/challenge/claim EvidenceUnits, original literature/source refs, baseline evidence, dataset/resource/tool/code refs, and LLM/review artifacts. Paper/source refs are containers, not substitutes for claim-level units.
- ResearchSlice persistence should split into core decision/provenance/resource-trace tables. At minimum, keep ResearchSlice, EvidenceRef, Boundary, and Assumption queryable rather than only JSON; option, selection, review, and artifact details may use payloads only where key state/risk/ref fields are still columns.
- Use ResearchSlice to constrain TopicQuestion, feed TopicValueAssessment, snapshot TopicPackage boundaries, and anchor UI/recheck. Do not treat it as title, topic value, publishability judgment, or a direct PaperProject promotion object.
- FormTopicQuestion consumes ResearchSlice boundaries, target setting/community, contribution type, claim shape, evaluation path, assumptions, resource trace, and usage contract to produce a TopicQuestion plus answerability plan stub.
- TopicQuestion must bind a source ResearchSlice version and preserve excluded boundaries. It is not a wording rewrite or a new unmet need; if it lacks answerability or violates boundaries, loop back to ResearchSlice first.
- `TopicQuestionContract` should be a versioned child record of TopicQuestion, not a separate chain node. It freezes the admitted question's boundaries, need inheritance, evidence refs, claim limits, answerability route, constraints, downstream usage contract, and contract hash for ValueAssessment/Package/Promotion consumption.
- `QuestionContract` data must come from frozen upstream refs only: ResearchSlice.version, admitted TopicQuestionCandidate, TopicQuestionSelectionDecision, Need/Evidence/Boundary/Assumption refs, EvidenceStrengthAssessment, ResearchConstraintProfile, and FormTopicQuestionRun input snapshot. Do not let unadmitted candidates, new LLM background, full paper text, or downstream ValueAssessment/Package judgments become contract sources.
- `TopicQuestionFalsificationCondition` should be a structured child of the contract. It captures hard, soft/degradation, and answerability failure conditions that would revise, lower, park, drop, or recheck the current question contract; ordinary risks stay in risk/open-dependency records.
- One ResearchSlice may produce multiple TopicQuestion candidates. Use a TopicQuestionCandidateSet and SelectTopicQuestion before TopicValueAssessment; each admitted question needs its own boundary check, answerability plan stub, claim alignment, and review state.
- FormTopicQuestion should be a persisted workflow run, not a single prompt. Freeze ResearchSlice/version, resource trace, EvidenceMap/SearchPlan/SearchRun versions, ResearchConstraintProfile, and upstream artifacts as the input snapshot.
- FormTopicQuestion should use role-separated agent review: question framing, candidate generation, answerability planning, boundary review, evidence trace review, claim-shape review, community-fit review, and synthesis. Treat disagreements as review artifacts rather than votes.
- TopicQuestion selection should first enforce hard blockers, then independently review per-candidate readiness and candidate relationships such as duplication, conflict, complementarity, dependency, and fallback value.
- Persist FormTopicQuestionRun, QuestionFormationReviewSession, TopicQuestionCandidateSet, and TopicQuestionSelectionDecision. Store full prompt/response/transcript artifacts outside the DB, but keep identity, version, state axes or derived display status, blockers, admitted/rejected reasons, blocking contexts, and artifact refs queryable.
- Make FormTopicQuestion robust by failing early on incomplete ResearchSlice inputs, deriving candidates from a frozen QuestionFrame, separating evidence-backed fields from assumptions, and preserving negative question memory for repeated rejected/parked forms.
- Use deterministic validators for schema, refs, boundary ids, state-axis enums, and artifact refs before relying on LLM semantic review. Re-run instability on the same input snapshot should trigger stability review rather than silently accepting the newest recommendation.
- Every FormTopicQuestion failure should emit a typed loopback target and required actions. Do not rerun without new evidence, constraints, slice version, question axis, or explicitly accepted risk.
- SelectTopicQuestion is a separate persisted admission/disposition decision over TopicQuestionCandidateSet. It consumes the candidate set, FormTopicQuestion input snapshot, source ResearchSlice, evidence refs, ResearchConstraintProfile, negative question memory, and downstream readiness hints.
- SelectTopicQuestion should use hard gate -> per-candidate admission/readiness review -> candidate relationship review -> admission disposition decision. It does not decide topic value, does not default to one-winner selection, and does not own a loopback mechanism.
- Persist TopicQuestionSelectionDecision with admitted ids, per-candidate hard gate results, admission review, candidate relationships, rejected reasons, blocking contexts, human review triggers, confidence, reviewer artifacts, and created TopicQuestion refs.
- From ResearchSlice to TopicQuestion, persist separate layers: source ResearchSlice refs, FormTopicQuestionRun, frozen QuestionFrame, TopicQuestionCandidateSet/Candidate, TopicQuestionSelectionDecision, materialized TopicQuestion, trace refs, and artifact refs.
- Existing TitleCardResearchQuestion can evolve as the materialized TopicQuestion object, but its current researchSlice string and JSON source refs are insufficient for the new workflow.
- TopicQuestion and TopicQuestionCandidate should preserve inherited Need traceability via TopicQuestionNeedRef / TopicQuestionCandidateNeedRef derived from ResearchSliceNeedRef. These refs point to ValidatedNeed and source NeedCandidate; they do not revalidate the need.
- Candidate, question evidence refs, boundary refs, and assumption refs should be queryable. Long prompts, transcripts, and review narratives belong in artifact storage with checksums.
- Rejected and parked TopicQuestion candidates should remain persisted so they can serve as negative question memory for later formation runs.
- TopicSeed / TitleCardIntentProfile should be a versioned intent contract under TitleCard, not the same object as TitleCard. Keep TitleCard as the UI/aggregate object.
- Add SeedDiscoveryRun as an optional literature-to-seed automation layer. It should consume literature/resource-pool snapshots, index/cluster/search configs, source refs, and user-profile context, then produce SeedCandidateSet rather than formal TopicSeed records.
- SeedCandidate must not be consumed by SearchPlan directly. Accepted candidates should pass through NormalizeAndReviewSeed and human confirmation/editing before creating a TopicSeed version.
- Persist SeedDiscoveryRun, SeedCandidateSet, and SeedCandidate with provenance, cluster refs, workflow/model/tool versions, quality warnings, and artifact refs. Treat inferred user preferences and constraints as assumptions until human-confirmed.
- Make SeedDiscoveryRun robust with multi-source discovery, negative evidence fields, rerun/strategy stability checks, evidence-density checks, merge/dedup rationale, and low-priority parking for sparse or trend-biased candidates.
- SearchPlan must reference a concrete TopicSeed version. Seed revision, split, close, or reopen should create a new version or supersession record rather than mutating historical intent.
- NormalizeAndReviewSeed can use LLM to structure raw title-card text, detect ambiguity, generate clarification questions, propose seed splits, and recommend ready_for_search_plan. LLM-generated constraints must remain assumptions until human-confirmed.
- After TopicQuestion admission, the workflow should become mostly linear: run TopicValueAssessment per admitted question. Linear control flow does not mean shallow assessment.
- TopicValueAssessment consumes TopicQuestion, inherited need refs, ResearchSlice, evidence refs, ResearchConstraintProfile, and decision memory. It decides whether the current question contract is worth investing in now.
- Build a TopicValueAssessmentInputSnapshot before assessment. Required sections are question_contract, need_trace, slice_snapshot, evidence_digest, and constraint_snapshot; optional drilldowns include EvidenceUnit locators, SearchRun/SearchPlan provenance, historical assessments, and reviewer artifacts.
- TopicValueAssessment should not default to consuming full paper text, unrelated EvidenceMap nodes, all non-admitted candidates, or TopicPackage/title candidates.
- TopicValueAssessment should produce minimal gates, evidence-backed ValueReasoningMemo, ceiling/base/floor scenario sketch, top reviewer objections, ValueDispositionDecision, and cited reasons. It should not rewrite TopicQuestion, generate title/package, directly create PaperProject, or default to complex multi-agent debate.
- ValueReasoning should be persisted as a structured ValueReasoningMemo, not as only scores. Include value thesis, significance, originality, claim leverage, reviewer risks, effort-to-value, strategic fit, negative memory check, and disposition bridge.
- ValueReasoningMemo may recommend a disposition, but formal state movement belongs to ValueDispositionDecision. Use a focused critic for high-uncertainty advance_to_package/drop recommendations or high-severity reviewer objections.
- TopicPackage should be created only from ValueDispositionDecision.advance_to_package records, and the result is a draft handoff package. If multiple TopicQuestions advance, create one draft package per question in v1; later PromotionDecision can choose, combine, or hold.
- TopicPackage is a handoff snapshot, not another value gate. It consumes TopicQuestion, ValueReasoningMemo, inherited need refs, ResearchSlice, evidence refs, and constraints to produce title candidates, background, contribution summary, evaluation plan stub, evidence summary, risk register, and handoff notes.
- Keep TopicPackage comparatively simple: implement it as a linear template-based builder with deterministic trace/boundary/readiness checks. Use LLM only for wording and package composition, not for adding new needs, evidence, claims, boundaries, or value dispositions.
- Existing TitleCardPackage can evolve as TopicPackage, but package provenance should eventually include source TopicQuestion, TopicValueAssessment, ResearchSlice version, ValidatedNeed refs, selected Evidence refs, snapshot hash, and artifact refs.
- PromotionDecision is the human authorization gate from TopicPackage to PaperProject. LLM may build the dossier, run blocker checks, summarize resource/strategy fit, and recommend a disposition, but must not auto-approve promotion or create the project.
- PromotionDecision should support promote, promote_with_conditions, merge_packages, refine_package, reassess_value, revise_question, revise_slice, recheck_evidence_or_search, park, and drop. Non-promote outcomes need typed loopback targets, required actions, source refs, and reopen conditions where relevant.
- `PromotionCommitmentProfile` should be persisted as a child of PromotionDecision. It is the human-confirmed commitment snapshot for scope, claim ceiling, non-negotiable boundaries, allowed refinements, accepted risks, required conditions, early checks, and stop/reopen conditions; it is not another value gate or a PaperProject execution plan.
- Persist PromotionDecision in the local DB with package refs, decision maker, decision type, conditions, unresolved risks, loopback target, required actions, downstream project ref, and artifact refs. Long dossiers and review transcripts belong in artifact storage.
- Persist PaperProjectBridge as the audit boundary from topic selection to paper project management. It should link PaperProject back to PromotionDecision, TopicPackage, TopicQuestion, ResearchSlice, ValidatedNeed, and selected evidence refs.
- PaperProjectBridge should use refs for upstream authority and copy only editable project-starting text into PaperProject, such as project brief, title candidates, question wording, contribution summary, evaluation plan stub, risk register, and evidence digest.
- Persist PlanResearchSliceRun, ResearchSliceOptionSet, SliceSelectionDecision, and ResearchSlice in the local DB. Store large prompts/responses/comparison diagnostics as artifacts, but keep input snapshots, workflow/model/prompt versions, option identities, selected/rejected reasons, open risks, and recheck flags queryable.
- Persist SlicePlanningDebateSession as a child of PlanResearchSliceRun. Keep roles, round summaries, key objections, accepted/unresolved disagreements, human-review triggers, and transcript artifact refs queryable; store full transcripts/prompts/responses as artifacts.
- ResearchConstraintProfile should be versioned/snapshot-able. Constraint changes create a new planning run rather than rewriting previous option sets; EvidenceMap/ValidatedNeed/SearchPlan/SearchRun changes propagate recheck_required downstream.
- Candidate rejection and seed/title-card closure should preserve reasons and refs; closed seeds can be reopened only with new evidence, changed constraints, or new SearchPlan rationale.
- Implement recheck as an event-driven cross-cutting mechanism. Workflows emit structured state_signals; only cross-node impacts create RecheckEvent records.
- Persist RecheckEvent, RecheckImpact, and RecheckResolution in the local DB. Use deterministic gates and human review for key blocking, dismissal, override, and resolution decisions.
- Treat recheck as a ledger, not v1 automation. RecheckEvent records the change, RecheckImpact scopes the affected objects and impact level, and RecheckResolution closes the impact; v1a should not implement automatic cascade propagation, background scheduling, full workspace scans, or automatic reruns.
- Use event_fingerprint, impact_dedup_key, cooldown windows, retry_budget, and stop_conditions to prevent recheck storms. Recheck propagation must be lineage/ref-limited, and second-order propagation requires a new assessment or gate trigger.
- Only RecheckImpact/RecheckResolution through the control plane may update freshness_status. LLM state_signals are proposals, not authoritative state writes.
- AcceptedRisk should reopen only when its expiry/recheck condition is met, new evidence falls outside the accepted scope, severity escalates, or a human/gate decision explicitly reopens it.
- Do not split RecheckEvent/RecheckImpact/RecheckResolution by v1a/v1b/v1c. Keep one model and use origin_stage, affected_stage, handling_profile, policy_version_id, blocks_transition_keys, and affected object set to express phase-specific behavior.
- Add input_state_context to critical workflow snapshots and state_signals to workflow outputs so agents, UI, local queues/future scheduler, and gates consume the same state model.
- Split object state into orthogonal axes instead of one overloaded status field. Persist lifecycle_status, decision_status, review_status, freshness_status, execution_status, and permission_status where applicable; treat any legacy/composite `status` as a UI/read-model convenience, not the sole gate input.
- RecheckEvent/RecheckImpact should update freshness/impact state, not rewrite historical decisions. For example, an accepted human-confirmed ValidatedNeed can become freshness_status=recheck_required while decision_status remains accepted.
- Separate content provenance from functional lineage. Literature-owned paper/source/dataset/code/note objects are content containers; TopicSeed/SearchPlan/ResearchSlice/TopicQuestion/TopicPackage are functional containers.
- Persist functional lineage and trace snapshots with enough structure to drill from PaperProjectBridge back to TopicSeed and from EvidenceRef back to EvidenceUnit and source locator.
- Module boundaries should pass refs, snapshots, bridges, and working copies only. Downstream modules should emit recheck/feedback events instead of mutating upstream topic-selection objects.
- Model human-in-the-loop gates with four permission levels: draft_only, agent_actionable, human_confirmed, and human_override_only.
- Persist HumanConfirmedDecision and HumanOverride records. Overrides must include blocker id/type, overridden risk, scope, expiry or recheck condition, and must be visible as accepted_risks in downstream workflow snapshots.
- Persist `AcceptedRisk` as the unified risk acceptance object for pass_with_risk, HumanOverride, CoverageRiskAcceptance, value disposition risks, promotion conditions, and recheck dismiss/defer decisions. It is distinct from HumanOverride and does not resolve blockers.
- Every `AcceptedRisk` must include source ref, risk type, severity, accepted_by, scope, affected transitions, downstream visibility, expiry/recheck condition, and active/expired/resolved/superseded status. Downstream workflow input_state_context must expose relevant active risks.
- Add a versioned `BlockerPolicy` layer before HumanOverride. Classify blockers as non_overridable, overrideable_with_risk, or escalation_only; trace/ref/schema/legal/auth blockers must be fixed rather than overridden, while coverage/resource/confidence/secondary-evidence blockers may continue only with HumanOverride plus accepted risk.
- ReadinessGateResult should include blocker policy ids/categories. Recheck and gate workflows must not treat accepted risks as resolved blockers; downstream input_state_context must expose them explicitly.
- Define the unified control plane as `DecisionChainControlPlane`: runtime semantics with a harness-first v1 implementation. It is the authority for transition entry, state-axis writes, transition audit, permission policy, readiness gates, human gates, overrides, and recheck event recording.
- Do not implement a full long-running runtime in v1. Defer automatic multi-node scheduling, priority queues, cancellation/recovery, concurrency locking, automatic retry, and full-chain recheck propagation until the evidence-to-need quality loop proves the need.
- Do not use pure workflow harnesses as the control plane. `WorkflowHarness` may run LLM/agent workflows and produce `LLMWorkflowRun`, artifacts, state_signals, and recommendations, but it must not directly write authoritative state, create human-confirmed objects, dismiss blockers, or bypass TransitionPolicy.
- Persist `TransitionPolicyVersion` and `ChainTransitionAttempt` as cross-cutting control records. Every critical transition should record transition_key, source/target refs, input_state_context, policy_version_id, gate_result_id, workflow_run_id, human/override refs, result, output refs, state transition refs, and recheck event refs.
- Treat semantic-pollution control as a control-plane responsibility. Add `ContextPolicyVersion`, deterministic `ContextCompiler`, and persisted `InputSnapshot` in v1a; `AgentOrchestrator` must not decide whether transcript, memory, signal, or raw artifact text can be used as evidence.
- Every critical LLM workflow must consume a compiled `InputSnapshot`, not self-assembled context. Snapshot items should expose semantic_role, allowed_use, freshness_status, source_version, source_refs, and digest. Only authority objects and EvidenceUnit/source-locator-backed summaries can be used as factual support.
- v1a must prove the foundation mode, not only produce ValidatedNeed: ContextPolicy, InputSnapshot, WorkflowHarness, ReadinessGateResult, QualitySignal, ArtifactRef, RecheckEvent, and ChainTransitionAttempt must form a minimal closed loop.
- v1b and v1c reuse the same context policy/compiler. v1b adds workflow policies for slice/question/value/package, while v1c compiles a promotion-specific snapshot from frozen package/value/trace/risk/recheck refs. Neither stage may reintroduce direct raw-transcript or raw-artifact consumption.
- Treat artifact storage as `DB authority metadata + artifact store audit material`. Artifact originals are not fact sources; ArtifactRef/manifest is the queryable control record.
- Columnize ArtifactRef identity, storage_uri, checksum, byte_size, content_class, rights_class, retention_class, workflow_run_id, linked refs, expires_at, redaction_status, pinned_reason, and created_at. Do not hide these in business-object JSON.
- Use retention classes: authority_permanent, audit_long, review_packet_long, raw_run_short, debug_short, ephemeral_no_persist, and restricted_locator_only. Never persist provider secrets, hidden reasoning, transient token streams, unreferenced scratchpads, or unauthorized external full text.
- v1a artifact scope is manifest, checksum, retention class, pin/protected reason, and cleanup dry-run for LLMWorkflowRun, SearchRun, AgentReviewSession, ReadinessGateResult, and human decision support packets. Automatic deletion and global archival are out of v1a.
- v1b extends the same policy to slice/question/value/package artifacts and may add workflow-profile artifact budgets. v1c treats promotion artifacts as audit_long/review_packet_long and pins artifacts referenced by promote/promote_with_conditions decisions.
- Add `WorkflowProfilePolicy` to control LLM complexity. Profile escalation is basic -> focused_critic -> full_debate -> human_review; triggers come from deterministic gates, QualitySignal, DecisionMemory, evidence/coverage conditions, workflow self-signals, transition importance, or explicit human request.
- DecisionChainControlPlane chooses the workflow profile through TransitionPolicy/WorkflowProfilePolicy. LLMs may suggest profile escalation, but cannot self-upgrade to full debate or write authority state.
- WorkflowHarness starts the selected workflow run, while AgentOrchestrator only schedules roles/rounds inside that run. Global schedulers must not directly interpret QualitySignal or independently launch multi-agent debate.
- v1a defaults: GenerateNeedCandidates uses basic plus optional skeptic, AssessCandidateReadiness can use focused_critic because it is a gate, ValidateNeedAdjudication uses focused_critic plus human confirmation, and full_debate is policy-triggered only.
- Persist LLMWorkflowRun for every critical LLM/agent workflow. Keep workflow, prompt, model, tool versions, input snapshot refs, output refs, state signal summaries, human triggers, execution_status, and artifact refs queryable.
- Persist AgentReviewSession, LLMWorkflowOutputRef, PromptTemplateVersion, ModelProfile, and WorkflowQualityFeedback. Store full prompts/responses/transcripts/tool outputs/rerun diff reports as artifacts with checksums.
- Do not persist provider secrets, raw hidden reasoning/chain-of-thought, transient token streams, unreferenced scratchpads, or unauthorized external full text.
- Use the P0-P3 schema roadmap for implementation sequencing: P0 core identity/version/trace, P1 decision objects, P2 cross-cutting control, P3 expansion/optimization via thin records and payloads until query/recheck needs justify table splits.
- Do not hide query-critical fields in JSON. Columnize identity, state axes, version/supersession, refs, workflow run id, snapshot hash, artifact refs, evidence refs, impact level, recheck flags, human triggers, accepted risks, decision type, loopback target, and required actions.
- Implement ReadinessGateResult as the shared readiness/quality gate record for critical transitions. Deterministic gates should run before LLM readiness assessment, and human gates should run only when required or escalated.
- Gate results must columnize result, hard blockers, required actions, loopback target, human review flag, accepted risk refs, evidence/functional refs, workflow_run_id, and decided_by.
- Treat the full chain as target architecture, not v1 scope. Split implementation into v1a/v1b/v1c. v1a ends at ValidatedNeed and validates the evidence-to-need quality loop; v1b covers ResearchSlice/TopicQuestion/ValueAssessment/TopicPackage(draft); v1c covers PromotionDecision/PaperProjectBridge.
- v1a authority tables should cover TopicSeed, LiteratureResourcePoolSnapshot, SearchPlan, coverage child records, SearchRun, EvidenceMap/EvidenceUnit, NeedCandidate, CandidateDecisionMemory, ValidationDecisionSupportPacket, ValidatedNeed, ReadinessGateResult, LLMWorkflowRun, ChainTransitionAttempt, HumanConfirmedDecision, and minimal AcceptedRisk.
- v1a thin persisted records may cover SeedDiscoveryRun, SeedCandidate, EvidenceStrengthAssessment, SearchPlanRecheckRequest, RecheckEvent/RecheckImpact, HumanOverride, and AgentReviewSession. Keep stable ids, key states, refs, payloads, and artifact refs without over-tableizing.
- ResearchSlice, ResearchSliceOptionSet, SliceSelectionDecision, TopicQuestion, TopicQuestionContract, TopicValueAssessment, ValueDispositionDecision, TopicPackage, PromotionDecision, and PaperProjectBridge are not v1a active gates. Preserve their target contracts, but do not make them v1a implementation scope.
- v1b is Need-to-Draft-Topic. It starts from human-confirmed ValidatedNeed plus traceable evidence/search versions and a lightweight ResearchConstraintProfile, and ends at TopicPackage(draft). Its authority/gate objects are ResearchSlice, SliceSelectionDecision, TopicQuestion, TopicQuestionContract, TopicValueAssessment, ValueDispositionDecision, TopicPackage(draft), ReadinessGateResult, ChainTransitionAttempt, and AcceptedRisk.
- v1b workflow/support objects include PlanResearchSliceRun, ResearchSliceOptionSet/Option, SliceSelectionReviewSession, FormTopicQuestionRun, TopicQuestionCandidateSet/Candidate, TopicQuestionSelectionDecision, QuestionFormationReviewSession, and ValueReasoningMemo. PromotionDecision and PaperProjectBridge remain out of v1b scope.
- v1c is DraftPackage-to-PaperProjectBridge. It starts from TopicPackage(draft) with passing trace/boundary checks and visible blockers/accepted risks, then runs PromotionDecisionSupport, PromotionGateCheck, HumanPromotionDecision, PromotionDecision, PromotionCommitmentProfile, and PaperProjectBridge.
- v1c only creates or connects PaperProjectBridge when PromotionDecision.decision is promote or promote_with_conditions. Full PaperProject execution planning, writing agents, experiment automation, and research-argument workspace implementation remain outside v1c.
- v1c is an authorization bridge, not another topic-value assessment and not PaperProject execution. PromotionDecision must be human-confirmed, PromotionGateCheck must verify trace/boundary/risk/recheck consistency, and PromotionCommitmentProfile must freeze scope, claim ceiling, accepted risks, early checks, allowed refinements, and stop/reopen conditions.
- PaperProjectBridge passes upstream refs, snapshot hashes, and editable working-copy text downstream. PaperProject may evolve execution work, but downstream issues must return as feedback/recheck events or new versions, not upstream authority rewrites.
- The v1a/v1b/v1c sequence covers the current topic-selection management requirements and downstream traceability bridge, but not full paper execution. Remaining design-risk closures still need focused contracts for CoverageMatrix layering, AcceptedRisk, LiteratureResourcePoolSnapshot, EvidenceStrengthAssessment triggers, recheck storm prevention, human review UI, negative memory reuse, and system evaluation.
- Treat v1a as a title-card reviewer workbench, not an automatic topic-generation product. Its only successful business exit is a human-confirmed ValidatedNeed with source seed, SearchPlan/SearchRun/EvidenceMap versions, supporting/challenge EvidenceUnits, accepted risks, unresolved gaps, recheck policy, and validation packet refs.
- Keep v1a UI focused on Seed Overview, SearchPlan Panel, EvidenceMap/Evidence Drilldown, NeedCandidate Review Cards, and ValidatedNeed Decision Surface. ContextPolicy, InputSnapshot, LLMWorkflowRun, ArtifactRef, QualitySignal, and ChainTransitionAttempt are trace/audit drilldown objects, not primary workbench objects.
- Make ValidatedNeed creation and high-impact SearchPlan scope changes the strong human-review points in v1a. SearchPlan drafts, SearchRuns, EvidenceMap building, NeedCandidate generation, readiness assessment, SearchPlan revision proposals, and validation packets can be agent-actionable under control-plane gates.
- Implement trace integrity as deterministic-first gate logic. v1a checks must cover ref existence, version/snapshot hash consistency, EvidenceUnit -> ContentRef -> source locator chain, semantic-use violations, freshness/recheck state, and rights/source health for NeedCandidate readiness and ValidatedNeed creation.
- Trace integrity failures should become ReadinessGateResult blockers, QualitySignal(trace_integrity), and, when action is required, DecisionWorkQueueItem blocker/recheck records. LLMs may explain failures but must not decide trace validity.
- Treat DecisionWorkQueue as a control-plane work ledger. Queue items are derived from gate/recheck/signal/workflow/accepted-risk/downstream events through policy; raw signals are not queue items and must not be shown directly as tasks.
- v1a queue implementation should support queue type, target ref, priority, blocking transitions, dedup key, status, allowed handlers, retry/cooldown, and supersession. Defer background scheduling, automatic cascade reruns, automatic dismiss, and global priority optimization.
- Cross-module APIs should use versioned envelopes with refs, snapshot_hash, payload_hash, idempotency_key, actor, policy_version_id, and artifact refs. v1a only needs Literature/TitleCard-to-TopicSelection contracts; v1c adds PaperProjectBridge commands and downstream feedback/recheck APIs.
- Do not replace the existing TitleCard model in one migration. Use adapter/read-model compatibility and sidecar authority objects over the current TitleCard, TitleCardResearchRecord, TitleCardNeedReview, TitleCardResearchQuestion, TitleCardValueAssessment, TitleCardPackage, and TitleCardPromotionDecision tables.
- Treat TitleCard as the canonical origin surface / TopicSeed container. TitleCardEvidenceSelection remains an evidence basket input, not EvidenceMap; v1a creates LiteratureResourcePoolSnapshot/EvidenceMap/EvidenceUnit beside it.
- Treat legacy TitleCardValueAssessment.verdict=promote as `advance_to_package` compatibility semantics only. PaperProject promotion authorization belongs exclusively to human-confirmed PromotionDecision.promote/promote_with_conditions.
- Keep legacy refs. New authority objects should preserve FunctionalRef, TraceSnapshot, legacy_ref/sourceRecordIds, and artifact refs so old UI/API surfaces can progressively adapt without destructive table renames.
- Keep v1 UI focused on the existing desktop shell plus a title-card reviewer workbench. Define UI as six surface categories: App Shell / Navigation, Workspace / Title-card Workbench, Decision Review Surfaces, Queue Surfaces, Trace / Evidence Drilldown, and Settings / Policy Surfaces.
- Decision Review Surfaces should make confirmation scope, evidence, challenge, blockers, accepted risks, required actions, and downstream effects visible. They must not reduce research judgment to a score or recommendation button.
- Queue Surfaces should handle human review, recheck, blockers, accepted risk expiry, and failed/partial workflows as focused work queues that link back to decision review or trace drilldown.
- New UI must stay on the data-ui/token/contract path and must not expand the frozen legacy compatibility layer.
- Split TopicValueAssessment into ValueReasoningMemo and ValueDispositionDecision. Use advance_to_package/refine_question/refine_slice/park/drop for value disposition; reserve promote for PromotionDecision.
